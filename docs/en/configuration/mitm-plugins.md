# Plugin Configuration

`plugins` independently manages ordered plugin instances, while `mitm` manages the HTTP switch, client admission and body budget. The top-level `certificate` section manages the CA shared by API HTTPS and MITM. The default build includes `surge`, supporting HTTP/DNS sgmodules. The JavaScript backend is selected at build time: QuickJS by default, or Node.js with `make SURGE_RUNTIME=nodejs`. First-party plugins are maintained under `plugins/` and share the core Go module and version. Copy [plugins.cfg.example](../../../plugins.cfg.example) to a local `plugins.cfg` to choose what to build, uncommenting optional plugin entries as needed. Git ignores the local configuration and generated registry; without a local configuration, the selections in the example are used. Advanced DNS routing and caching are two optional plugins; see [DNS](dns.md).

```text
mitm {
  enabled: true
  client_source_address: '02:00:00:00:00:50'
}
plugins {
  surge {
    module { personal: 'file:modules/personal.sgmodule' }
    script_timeout: 5s
  }
  work {
    type: surge
    module { work: 'file:modules/work.sgmodule' }
  }
}
```

The subsection name is the instance ID and the default type. Use `type` for multiple instances of the same type. When the instance name equals its type and there are no private parameters, `plugins { youtube: true }` is shorthand for `youtube {}`; `youtube: false` is equivalent to `youtube { enabled: false }`. Configuration output prefers this shorthand and omits a matching `type` and the default `enabled: true` from blocks, without omitting private parameters. Both forms share instance-name, duplicate-ID and boolean validation; shorthand accepts neither functions nor annotations. The system diagnostic reserves the instance name `dae-mitm-test`.

Surge's `store` defaults to `true`, automatically saving to `DAE_LOCATION_CACHE/plugins/<ID>/surge-store.json` by instance ID. Instances have separate data; `store: false` switches to instance-local memory storage. Instances are enabled by default and can be disabled with `enabled: false`. The HTTP master switch defaults to off and does not affect DNS, routing or background tasks. Unknown enabled types, duplicate IDs and unknown fields of enabled plugins are errors. Disabled plugins skip configuration parsing, resource preparation, instance construction and background tasks; their types need not be compiled in, and their private configuration may remain in place.

At startup and reload, dae first checks that the types of all enabled instances were compiled in, then calls `Configure` to parse and validate each instance's configuration and obtain runtime resource factories. Only then does it prepare subscriptions, eBPF, connectivity checks and remote modules. For example, if a later bilijump instance was not compiled in, dae reports the error immediately rather than waiting for an earlier Surge module download. An ordinary `dae reload` refreshes external resources declared by plugins, compares effective configuration and resource contents, and rebuilds only changed instances. Built-in Surge compares module contents and their dependent scripts. A failed refresh uses a complete valid cache or rejects the reload; resource failure is not interpreted as instance deletion. Static validation or resource preparation failure preserves the current control plane; see the [Plugin API](../../../component/plugin/README.md#configuration-preflight-and-preparation).

Place `client_source_address` in `mitm`, and module, store and JS limits in the Surge instance. The daemon prepares a shared persistent CA whose public certificate is available through the Unix API, independently of TCP API listening or MITM. Use the top-level `certificate` section for an existing certificate; see [Local CA](certificate.md). DNS, IP Host and routing plugins themselves neither depend on nor create a CA. Client switches control only HTTP/MITM. Relative paths are based on `DAE_LOCATION_CACHE`. Module and dependency caches are stored under `resources/surge`, controlled centrally by `global.resource_cache`.

`buffer_memory_limit` belongs to the host, defaults to `268435456` (256 MiB), and provides a process-wide shared budget for managed body buffers. It covers body snapshots, Surge decompression and rewrite output, script HTTP responses and pending callback data. Data still needed for unfinished forwarding, read-only borrowing or request retries continues to count against the budget. Capacity is reserved before allocation; growth counts both old and new capacities simultaneously. Insufficient budget returns immediately rather than holding a partial reservation while waiting for other requests. Surge skips the current processing step and forwards the original content, preserving earlier rules that were successfully applied; script HTTP requests report failure through their callback.

After a reload is published, old and new hosts share the budget using the smaller of their two limits; the new limit takes effect once the old host exits. Candidate preparation does not change the active budget, and lowering the limit does not discard existing bodies. `dae plugins status` displays current usage, the effective limit, the process peak and rejected reservation count. This budget is not an RSS limit. It excludes JavaScript engine memory, temporary JSON/base64 bridge objects between host and scripts, jq worker intermediates, plugin-owned allocations, caches and network protocol buffers. Per-script `memory_limit`, body-size and concurrency limits still apply.

The module section emitted by `dae plugins surge configure` can be placed in the selected Surge instance.

Plugins execute in declaration order: request A → B → upstream, response B → A. Each plugin evaluates its scope independently, using the host and port admitted for the current request before plugin execution. URL/Host rewrites do not activate another scope. Within a Surge instance, the original module order and the behavior of running only the first matching script in each direction remain unchanged.

Admitted HTTPS/HTTP/2 and HTTP/3 connections allow cross-host request coalescing on the same port, including application authorities not covered by the single-host certificate. Requests outside every HTTP scope skip all plugin request/response hooks and preserve the original Alt-Svc. Unless a plugin explicitly rewrites the URL scheme, host or port, all streams retain the original ingress target, outbound, mark and upstream TLS identity. Authority changes do not trigger another DNS lookup or routing decision; the original endpoint dispatches by HTTP authority. Changes only to path/query or the Host header do not change the network target. Only explicit URL-target rewrites and plugin-initiated requests resolve, route and verify TLS for a new target. `domain()` routing matches the actual ingress target; it is not a filter for each stream's application authority. The `Flow.Host` provided to plugins is the application authority, not independent authentication evidence; `Source/Destination` retain the captured addresses. Port changes and HTTP/1 cross-host requests still return 421.

Inbound HTTP/2 preserves the original `:scheme`. If it is inconsistent with the ingress connection, dae returns 421 before executing plugins or selecting an upstream. `:scheme=http` over TLS HTTP/2 is not normalized to HTTPS. Explicit port changes, invalid authorities and scope checks remain enforced. See [Request scheme (Chinese)](../../zh/design/mitm-http.md#请求-scheme).

The downstream handshake issues only a local single-host certificate and does not probe the upstream certificate. Certificate selection is independent of scope, script stage and `PreserveRoute`. The local issuance cache holds at most 256 entries; leaf validity is capped at 24 hours and the CA's expiry. Actual forwarding still verifies the certificate name, validity and trust chain of the upstream endpoint, returning an upstream error on failure. Local responses require no dialing. A block on the original target does not prevent a plugin from first generating a local response or rewriting to an allowed target. See [MITM HTTP forwarding and certificate identity (Chinese)](../../zh/design/mitm-http.md).

Each `Plan.Scopes` entry holds both capture scope and routing properties. Routing is determined after HTTP processing by default; a pure inspection that preserves the target and always forwards may declare `PreserveRoute: true`. Request processing takes priority in overlapping scopes. Surge automatically classifies modules containing scripts, URL Rewrite or Map Local as request-routed. Request-routed connections first pass scope and client admission, then execute HTTP rules, and finally determine outbound, mark, must and block from the effective target. A block on the original target does not prevent an admitted request from being rewritten to an allowed target; a block on the new target still rejects it. Pure inspection preserves the existing kernel route; unadmitted connections follow ordinary routing. Forwarding and script subrequests share connection pools isolated by target, node, outbound and mark, and traffic statistics are attributed to the actual upstream connection.

**eBPF direct forwarding is a core dae behavior.** The host generates TCP/UDP capture conditions from positive domain/IP entries and their respective ports in HTTP scopes. Only candidate connections enter userspace; unrelated direct SSH, HTTPS and other traffic continues to bypass userspace in the kernel. Capturing all TCP/UDP traffic or capturing by port alone must not compensate for missing domain information.

Domain conditions reuse the ordinary `domain()` DNS domain-to-IP mappings; literal IP conditions require no DNS. Without a mapping, a connection that would normally go direct in the kernel is not captured merely because a matching SNI/Host might appear later. Connections already entering userspace due to other rules can still be handled by their actual hostname. Shared IPs and positive wildcards may introduce extra candidates, but the original hostname, port, scope exclusion order and client switch ultimately determine whether plugins run. An exclusion in one scope does not cancel an allowance in another.

A client's resolved addresses may be out of sync with dae's current domain-to-IP mappings, for example when a device retains an old address after switching networks. On restart, dae restores the on-disk registry with its original expiry times; reloads inherit the in-memory table. Unobserved or expired mappings cannot support positive domain capture. See [DomainRegistry](dns.md#persistence-and-diagnostics).

HTTP/3 uses the same CA, client switch and plugin scopes, with no separate switch. Decryption begins only after a complete QUIC ClientHello declares `h3`. Both client requests and upstream connections use HTTP/3; plugin-initiated HTTP requests rematch TCP routing for the final target and use HTTP/1 or HTTP/2. Multiple connections and reconnections with the same source, destination and handshake domain are supported, as is same-port request authority coalescing. Cross-address migration and 0-RTT are unsupported. Downstream TLS session tickets are currently disabled. Requests matching a scope retain only H3 Alt-Svc advertisements for the request's host and port; ordinary forwarding outside scopes preserves the original Alt-Svc.

An explicitly captured connection using the `direct` outbound depends on dae forwarding and is disconnected when dae stops. This differs from uncaptured eBPF direct traffic.

Unchanged plugin instances retain background tasks, caches, in-memory state and metrics. A replaced instance cancels its background tasks only when it loses its last active host. After handoff, old protocol hosts drain HTTP requests already started, with a default 5-second drain budget; after the deadline they cancel requests and close connections. Instance resources close only after the last host releases the instance and background tasks exit. If the plugin's capture and routing declarations are unchanged, an instance update does not rebuild kernel routing. Background recognition, waiting budgets, caching and similar behavior are defined by each plugin; the host has no generic task queue and cannot modify a response after it has been returned.

`dae plugins status` and the Web Plugins section distinguish compiled types, configuration enablement, instance lifecycle and HTTP activation. The compiled list comes from the running daemon; it neither identifies configured instances nor infers them from a local `plugins.cfg`. Instance rows include disabled accepted configuration and the system MITM diagnostic. `scopes` counts effective HTTP scopes, while `declared_scopes` counts declared scopes. Disabled instances do not evaluate their Plan, report zero counts and have no `details`. `http_active` means effective scopes can participate in HTTP processing, not a guarantee of device interception or worker health; `http_reason` explains inactivity.

`--verbose` (`-v`) aggregates each plugin's full status output. The command queries the daemon once; `--instance ID` also selects disabled instances, without removing the process-wide compiled list or memory budget. Plugins without custom status output show their complete JSON report. Surge skips the absent `details` of disabled instances; other rendering failures retain the raw report and continue displaying other plugins, then return an error. `--json` outputs `compiled_plugins`, `buffer_memory` and `plugins`, taking precedence over `-v`. Status reflects only accepted configuration; failed reloads preserve the old state. Disabled-only configuration changes refresh status without replacing protocol hosts or the API handler. Ordinary `dae status` text does not expand plugin details.

Use `dae plugins surge status` to inspect Surge modules. External plugins may register commands such as `dae plugins bilijump status --instance personal`. Plugins without custom status output also have a generic status command. Commands query the daemon through the Unix socket and do not require `api.listen`. Certificate commands use `dae ca`. For status fields, see [Management page/API](api.md); for compilation, see the [Build Guide](../user-guide/build-by-yourself.md#external-plugins); for plugin development, see the [Plugin API](../../../component/plugin/README.md).

Plugins can also register Prometheus metrics through `Services.Metrics`, exposed alongside core metrics at `/metrics` on the unified API. Built-in Surge and the separate dns-cache and dns-router plugins already provide metrics. The host consistently adds `plugin_type` and `plugin_instance` labels. Metrics reset when an instance is rebuilt; see [Metrics and PromQL examples](metrics.md).

Go plugins can persist instance state through `Services.Storage`, which provides `Get`, `Put` and `Delete`. Each value is limited to 8 MiB, with atomic replacement and disk synchronization. Files reside under `DAE_LOCATION_CACHE/plugins/state/` (default base directory `/var/lib/dae`); new directories use `0700`, files `0600`. The default instance, whose name equals its type, uses `<type>/` directly; named instances use `<type>@<instance>/`, such as `plugins/state/bilijump/` and `plugins/state/bilijump@personal/`. Type and instance names are escaped separately for paths, including any `@` in a name, preventing state from being mixed across types or instances. Paths do not depend on the number of instances, so adding an instance does not move existing state. The same type and instance name reuse data across reloads and restarts; renaming or disabling an instance does not automatically delete files. The plugin defines the format, expiry and switches. By default, bilijump uses this API to save captured login Cookies; `persist_cookie: false` makes them memory-only. Reload restoration preserves their original expiry. See the [Persistent storage API](../../../component/plugin/README.md#persistent-storage) for development conventions.

## Troubleshooting intermittent HTTP / gRPC failures

Temporarily set `global.log_level` to `trace` to record MITM requests from ingress through the end of response processing. This also applies to pass-through modules that only declare capture domains and do not rewrite requests. Correlate events by `connection_id` and `request_id`. `path_id` is the first 16 hexadecimal digits of the SHA-256 digest of the escaped path without query parameters; use it to compare whether a failure and retry use the same path. `host` and `connection_host` identify the connection's original host; `request_authority` is the current request's normalized host and port. Invalid authorities are recorded only as `invalid`. Automatic diagnostics do not record raw paths, query parameters, authentication headers or bodies.

| Event | What to inspect |
| --- | --- |
| `mitm_request_begin` | Captured host, port, original source/destination addresses, client HTTP protocol and path digest |
| `mitm_certificate` | Local single-host certificate (`certificate_source=single`), certificate digest and DNS/IP SANs (`trace`) |
| `mitm_authority_coalesced` / `mitm_authority_rejected` | Accepted H2/H3 cross-host requests (`trace`; `plugin_scope=false` means plugins are skipped) or rejected authorities (`debug`), recording both connection and request host identities; the actual forwarding target is determined only after plugin execution |
| `mitm_upstream_connection` | Upstream connection local/peer addresses, `reused`, `was_idle`, `idle_ms`; transport retries may produce multiple events |
| `mitm_upstream_tls` / `mitm_upstream_written` / `mitm_upstream_first_byte` | TLS-negotiated ALPN, request-write and first-byte timing; `elapsed_ms` starts at this upstream forwarding attempt |
| `mitm_upstream_response` | Upstream HTTP status, protocol and declared body length; indicates only that response headers were received |
| `mitm_request_end` | Final HTTP status, total duration, body bytes read/written, `body_eof`, errors and final `grpc_status` |
| `mitm_response_failed` | Response body read or downstream write/flush failure; visible at `debug` |
| `mitm_http2_error` / `mitm_connection_end` | Client HTTP/2 protocol error (`debug`) and TCP connection end (`trace`) |

`mitm_request_end.outcome` distinguishes `completed`, `local_rejection`, `processing_error`, `transfer_error`, `aborted`, `canceled` and `upgrade`. `completed` means host HTTP processing finished; HTTP / gRPC status still needs checking. Bytes written represent body data passed to the HTTP server, not a client receipt acknowledgment. gRPC status is read after body EOF, supporting both normal trailers and trailers-only response headers. `missing` means no final status; `invalid` means malformed status. Upgrade tunnels do not record HTTP body byte counts.

A 421 `reason` distinguishes `scheme_mismatch` (the request scheme preserved by the interface differs from the transparent listener connection), `invalid_authority` (malformed), `authority_port_mismatch` (different port) and `authority_mismatch` (the protocol does not support cross-host requests). Other cross-host requests are not rejected locally. The upstream itself may still return 421; use `outcome` to identify local rejection. The same log `host` on one connection does not imply that every request has the same `:authority`: compare `connection_host` with `request_authority`. For scheme issues, compare `connection_scheme` with `request_scheme`. HTTP/2 `request_scheme` preserves the client's original `:scheme` for this comparison.

When an error occurs, record the time, retry normally once, and retain complete logs for several minutes before and after. For a systemd deployment:

```sh
sudo journalctl -u dae --since "10 minutes ago" -o short-iso-precise > mitm-failure.log
```

If there is no corresponding request-ingress event, continue checking capture mappings, TLS handshakes and the connection layer. The absence of `upstream_error` alone does not prove a complete response. HTTP 200 in the log does not imply gRPC success either. If body transfer fails after response headers are sent, the host aborts the HTTP/1 connection or resets the HTTP/2 or HTTP/3 stream rather than returning a truncated response as successfully completed.

HTTP capture checks client admission in eBPF before evaluating routing for the target scope. Device MAC overrides take precedence over configuration. Configuration accepts at most 4096 IP, CIDR, MAC or `all` entries, with the first match deciding allow or deny. An unknown MAC does not match MAC rules but may still match IP or `all`; IPv4 and native IPv6 prefixes match separately, and the default is deny.

Dynamic settings are published by replacing the entire table, and userspace routing reuses the same compiled result. Persistence or later commit failure restores the previous settings and kernel table; restoration failure is explicitly reported. After HTTP/MITM is disabled for a device, new ordinary direct connections remain kernel-forwarded; DNS, proxy and DNAT continue to follow their own rules. Existing connections retain their lifetime policy.
