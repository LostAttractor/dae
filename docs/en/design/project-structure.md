# Project Structure

dae builds on an eBPF data path, bringing only proxy traffic, DNS, and advanced-feature traffic matched by explicit rules into userspace. Components divide responsibility among rule compilation, control-plane publication, protocol resources, and application processing, preserving the kernel fast path for ordinary direct traffic.

| Directory | Responsibility |
| --- | --- |
| `cmd` | Command arguments, signal client, and application entry-point assembly |
| `internal/compiledplugins` | Plugin registry generated from local build configuration |
| `internal/daemon` | Startup, resource loading, differential reload, service publication, and shutdown |
| `config` | User configuration parsing and validation |
| `control` | Control plane, TCP/UDP forwarding, and kernel resource handoff; eBPF code is in `kern` |
| `component/routing`, `outbound` | Routing rules, destination plans, and outbound selection |
| `component/network`, `sniffing` | Interface management and protocol sniffing |
| `component/ca` | CA reading/writing, atomic initialization, public certificate export, and leaf-certificate caching; lifecycle managed by the daemon and shared by API and MITM |
| `component/mitm`, `component/pluginhost`, `component/plugin` | Protocol connection host, independent ownership of plugin instances/background tasks/storage/metrics, and public API |
| `plugins/surge`, `plugins/dns-cache`, `plugins/dns-router` | sgmodule support, DNS response caching, and DNS resolution policies and transports |
| `pkg/outbound` | Client protocols, transports, dial chains, and session primitives; independent of the dae control plane and application plugins |
| `pkg/config_parser` | Configuration parsing primitives; `grammar` holds the grammar, and `internal/dae_config` holds the generated Go parser |
| `api`, `api/client` | Public data contracts and standalone HTTP/Unix client |
| `client/cli`, `client/status` | Terminal commands and API status presentation |
| `web`, `internal/webui` | Independent frontend source and build, artifact embedding, and static hosting |
| `internal/apiserver` | TCP/Unix listeners, HTTP routing, authentication, request validation, and reload waiting; accesses the control plane through storage interfaces |
| `component/settings`, `component/clientset` | Settings persistence and client sets |
| `pkg`, `common`, `trace`, `third_party` | Foundation code, tracing tools, and pinned dependencies |

See [outbound connectivity and failover](../../zh/design/outbound-connectivity.md) for outbound runtime state and ownership, and [API authentication and access control](../../zh/design/api-access-control.md) for management-plane trust boundaries.

## Repository and Dependency Boundaries

First-party Go code uses the root `go.mod` / `go.sum`. The core, CLI, protocol libraries, parser, and application plugins are maintained in the same commit and released together with dae. Root-level documentation tools and `web/` share a pnpm workspace and the root `pnpm-lock.yaml`; the root `package.json` pins pnpm through `packageManager`. Web retains an independent build entry point and interacts with Go through API contracts, without depending on the Go toolchain. Third-party submodules are not part of the pnpm workspace.

`third_party/quic-go`, `third_party/quickjs-go`, and `kern/headers` are third-party dependencies pinned to specific commits. Upstream synchronization and library changes in forks are maintained in separate repositories; the main repository updates their references and verifies integration behavior. Routine first-party development does not require `go.work`; a local workspace can be used for integration with external plugins or forks.

Repository boundaries do not replace package responsibility boundaries. `component/outbound` manages outbound selection and runtime state, using dialing facilities from `pkg/outbound`; protocol libraries do not depend back on the control plane. The host invokes plugins through the `component/plugin` contract, with concrete implementations assembled only at the entry point. The CLI depends only on APIs, lightweight presentation packages, and plugin clients; Web accesses services through the HTTP API. Dependency checks enforce these directions.

`pkg/proxylink` provides link-label and Base64 parsing without runtime dependencies, shared by protocol libraries, subscriptions, and configuration. The outbound protocol library can be constructed, dialed, and closed independently; dependency checks allow it to reference only an explicit list of foundation packages.

## Plugins

MITM is optional. First-party application plugin implementations, tests, and documentation live in `plugins/`.
Copy [plugins.cfg.example](../../../plugins.cfg.example) to a local `plugins.cfg` to select plugins; the example is used when no local configuration exists.
The example enables only Surge by default, leaving DNS cache and router commented out for optional local enablement. Build-time selection neither creates runtime instances nor expands traffic capture.
`make` generates `internal/compiledplugins/plugins_generated.go`, and the complete Definition table, including static validation, resource preparation, factories, and commands, is passed through startup and reload.
Local selections and the generated registry are not version-controlled. Plugin report types, schemas, and client presentation belong to each plugin's own `api` / `client` packages; the core passes only generic reports and services.
Plugins depend on the [public API](../../../component/plugin/README.md), while the host owns transport resources.

The process `Runtime` owns shared network-interface listeners and the interface-name cache. Each control plane and DNS router instance registers callbacks through an independent scope. Closing a scope revokes and drains its own subscriptions; the source listener closes after all configuration generations have exited. A plugin scope can be reused across reloads with an unchanged instance, independent of a particular control plane's shutdown.

Each configuration generation also owns its protocol host, routing policy, and outbounds. Ordinary reloads retain a 30-second connection-preparation window for the old generation. If plugin instances are rebuilt, the old host drains first; late TCP/QUIC preparation and DNS requests that still require admission under the old host’s policy fail with `net.ErrClosed`, allowing clients to retry on the new generation. Ordinary TCP preparation also queries the host’s DNS address policy and is subject to this restriction. Reused instances retain the original window; new instances never execute requests with an old generation’s routing. See [connection state and reload lifecycle](connection-lifecycle.md) for the full contract.

Native [rules / DNAT](../../zh/configuration/destination-rules.md) and literal IP entries in Surge `[Host]` share dial-target rewriting; domain entries are answered through DNS plugins.

## TCP Forwarding

Connection preparation is separate from ongoing forwarding. DNS and MITM take over connections and use their own protocol lifecycles; ordinary forwarding uses a single coordination loop for bidirectional copying, half-close, draining, abort, and idle closure.

| File | Responsibility |
| --- | --- |
| `control/tcp.go` | Sniffing, routing, protocol takeover selection, upstream dialing, and the first write to proxy outbounds |
| `control/tcp_relay.go` | Takeover dispatch, statistics lifecycle, and bidirectional copy coordination |
| `control/tcp_copy.go` | Connection-pair endpoints, dependencies, and progress; unified copy results, counter finalization, and half-close |
| `control/tcp_splice.go` | Native TCP capability checks, sniffed-prefix writes, and standard-library `io.Copy` |
| `control/tcp_counters_linux.go`, `tcp_monitor.go` | Kernel write counters and Runtime-shared activity sampling and idle policies |
| `control/tcp_lifecycle.go` | Connection preparation tracking per configuration generation, shared connection ownership, and abort |

Proxy protocols that do not wait for a response defer their request headers until the first write. Within the dial budget, setup sends sniffed client data as the first write to the proxy outbound, combining the request headers and initial payload in one underlying write. If the client has not sent data, as with server-first protocols, the first upstream read during copying sends the headers separately. Direct connections have no proxy request headers; their sniffed prefix is written by the copy worker.

Before copying, both sockets and their counter capabilities are checked, then native or buffered copying is selected once. Original connection wrappers remain responsible for closing and releasing resources; native sockets are used only for copying and sampling. Each direction finalizes its counters before sending FIN, and the coordination loop waits for both to finish. Copy implementations neither hold routing configuration nor decide when to abort a connection.

A miss in the kernel flow-state LRU still checks for a live proxy socket in dae’s network namespace. Complete packets remain redirected, while first fragments are dropped rather than reverting to ordinary routing directly to the original destination. Kernel socket state owns this decision, without userspace timers or connection registries.

## DNS

The core's `dns_relay.go` / `dns_stream.go` transparently forward TCP/UDP port 53. `dns_observer.go` registers response evidence before delivery, including cache replay, while plugin observers run after successful delivery. Messages must be strictly parsed by `netutils.UnpackDnsMessage` before entering plugins or evidence observation. Domain evidence is organized by responsibility:

| File | Responsibility |
| --- | --- |
| `control/domain_registry.go` | Bidirectional domain/IP indexes over shared pairs, batch DNS registration, validation, deadline extension, and time-based GC |
| `control/domain_projection.go` | Per-IP AND/OR aggregation, capacity selection, and kernel publication |
| `control/domain_activity.go` | Activity normalization, coalescing queue and batch application, and exact pair/IP renewal |
| `control/domain_activity_conn.go` | TCP/UDP I/O observation adapters that preserve half-close capability |
| `control/domain_direct.go`, `control/domain_direct_feed.go` | Direct activity slots, generation tokens, ring reader, and loss recovery |
| `control/domain_capacity.go`, `control/domain_capacity_disk.go` | Byte accounting, omission buckets, durable deadlines, and bucket-aware recovery |
| `control/domain_registry_lifecycle.go` | One background loop for applying activity, GC, and persistence writes; shutdown and reload inheritance |
| `control/domain_registry_disk.go` | Binary baseline and log encoding/decoding, renewal-window handling, compaction, and crash recovery |

Userspace budgets the live index by estimated bytes per generation. If a new pair is omitted at capacity, its IP hash bucket is temporarily excluded from projection. The kernel selects a bounded subset of complete IPs with nonzero bitmaps by priority. See [DNS design](../configuration/dns.md). Advanced resolution policies and transports live in `plugins/dns-router`, and complete response caching in `plugins/dns-cache`; both are optional at build time and in configuration. Request order is Surge → router → core relay. The cache operates at the actual upstream exchange, regardless of declaration order.

### Transport Lifecycle

The core `dnsStream` owns the client TCP connection and correlates responses by ID and question. AXFR/IXFR subsequent frames are forwarded only after the first frame is delivered. The router's `transport.Exchange` owns the context, response copy, and socket for one upstream query, without sharing connections across queries. Concurrent UDP queries use separate sockets. Ordinary TCP queries may retry once on a new connection after disconnection, but are not retransmitted on a live stream. TLS transports verify the upstream hostname, and DoQ handles padding, FIN, and protocol errors.

Captured UDP DNS requests, including `must`, receive a non-reused 63-bit identifier per packet. The bounded `dns_handoff_map` stores the complete tuple, source, route, configuration generation, process name, and original return path. The identifier travels through the internal netkit/veth link in `skb->cb` to the peer, then is handed off through timestamp and mark with the same `recvmsg`. Userspace atomically retrieves and deletes the snapshot and checks the full tuple. Missing, truncated, or mismatched handoffs are dropped without falling back to the latest five-tuple record. Runtime owns the counter and maps across reloads; reaching the counter limit rejects requests rather than wrapping. LRU eviction only drops late packets and cannot change identity.

Ordinary DNS does not write to the return table shared by associations. Responses publish the request's immutable return path through a separate `dns_reply_map`; both transparent UDP and raw fallback pass the identifier using per-packet mark and `SCM_TXTIME`. The peer's fixed TCX egress verifies the identifier before the qdisc, moves it into trusted `cb`, and clears the synthetic timestamp and mark. The host verifies addresses, protocol, ports from the complete packet, and fragment boundaries before restoring the original interface and MAC. Return records remain until bounded LRU eviction, covering fragments that have not yet arrived. `must` still uses UDP associations, but before publishing routing, the kernel independently rechecks the active binding's device version, source, and LAN MAC. Userspace rechecks the immutable binding under the source serialization lock, preventing ownership from changing during queueing.

The core UDP relay borrows a maximum-message-size receive buffer from the existing buffer pool, then copies the response at its actual length after reading. The returned `DNSResponse.Wire` independently owns its bytes, and the temporary buffer returns to the pool when that relay call returns. Reusing the buffer for later queries cannot change a response already passed to a plugin or delivery endpoint.

Address-family preference probes use their own time budgets and TCP connections; canceling them does not close the client's shared stream. Failed or canceled queries do not publish response copies. I/O workers release connections, and cancellation returns without waiting for a blocking outbound `Close`.

The cache ages TTLs using the response's `ReceivedAt`. Before registering evidence, the core fills a missing timestamp with the delivery time. Cache hits preserve the original timestamp, and each delivery independently refreshes Registry retention.

### Evidence Lifecycle

Each domain has a bitmap, with the domain and IP indexes referring to the same pair deadlines. Activity observations extend only existing records, taking the maximum deadline. A monotonic evaluation-time watermark prevents delayed observations from reintroducing reclaimed evidence. Each IP node stores all associated domains and their AND/OR aggregation and priority. An all-zero bitmap also participates in AND to represent domain ambiguity on shared addresses.

Each domain record stores a lower bound on all its address deadlines. Registry organizes records into a min-heap by this lower bound; GC pops only records whose lower bound has arrived and scans their addresses. Renewals may leave a conservatively early lower bound; scanning removes expired addresses and recomputes it from remaining deadlines. Adding a pair immediately lowers its record's bound. Cold recovery and reload build the heap after installing all records. Pair additions and removals recompute aggregation per IP, while renewals only raise deadlines and relevant priorities. After a DNS response updates all associations in a batch, each affected IP publishes its complete state once. Kernel residency selection independently reads IP aggregates; pure renewals for resident IPs do not rewrite bitmaps. Applying observations advances the time watermark and checks for expiration.

Initial activity and DNS registration complete synchronously. Ongoing TCP/UDP I/O, MITM, and splice activity use a shared coalescing queue that retains only the greatest observation time per `(IP, domain or empty string)`. TCP callbacks normalize identity at construction. Traffic observation adapters wrap TCP connections accepted at ingress while preserving native sockets and `CloseWrite`. UDP stores normalized keys per original destination, retaining the sniffed name for the first destination and using IPs for others. Ongoing I/O is throttled per connection, or per destination for UDP, to at most one enqueue per second. TCP callbacks use an atomic deadline relative to a process-local monotonic baseline for lock-free checks; UDP compares the last enqueue time under the already-held endpoint lock. Initial activity is not throttled.

Userspace I/O observations share a sharded coalescing queue. The consumer first acquires the Registry lock, briefly locks all shards to swap two reusable buffers, then releases the shard locks. Renewal, GC, and kernel publication run outside the shard locks, so enqueueing does not wait for those Registry operations. All destinations share one batch boundary.

Kernel-direct activity uses generation-private slots, a ring buffer, and a loss counter. A slot is enabled only after the IP's bitmap has been successfully published. Membership changes rotate the token even when the bitmap is unchanged, so old samples cannot renew a different set of pairs. Full reconstruction writes eligible slots in batches; ordinary mutations write a slot by IP. BPF updates only existing slots by original destination IP and creates no flow state. The reader batches observations; under its lock, Registry requires residency, no pending update, and the current slot token before renewing at the original monotonic timestamp. A changed loss counter triggers bounded, nondeleting recovery batches. Stopping the reader does not hold the Registry lock. Rejected reloads can restart the predecessor's reader. Samples are not persistent state.

The owner calls `Start` once before publishing Registry. One background loop attempts to apply activity and check renewal-window expiration every second, checks GC every minute, and closes each renewal window and performs compaction. New pairs are appended by the mutations that create them. Writes begin only after successful activation. DNS registration, GC, renewal-window closure, and reload copying also apply previously queued activity first, preventing reclamation from deleting existing evidence prematurely or older activity for an unknown pair from applying to a newly registered pair. Validation and status reads do not consume the queue.

Shutdown marks the Registry retired and captures the final activity batch under the queue lock, applies it using the old window, then stops the background loop before the closing caller writes the last renewal window. Ordinary shutdown clears the queue's owner; handoff retains a handle to the retired Registry and continues accepting activity. Queue ownership and handoff state are protected by the queue lock, while Registry shutdown state is protected by the Registry lock. The new Registry copies pairs and their original deadlines, builds bidirectional indexes, installs bitmaps under current rules, switches the shared activity handle, then applies the captured handoff queue using the new window and runs GC before generating all IP aggregates. Subsequent enqueueing does not wait for aggregation or kernel publication.

Cold recovery and reload install records only into a new, unpublished Registry, using empty indexes allocated at construction. Disk recovery publishes records after fully validating the baseline and replaying the log; the caller holds the control-plane lifecycle lock to exclude concurrent shutdown. Reload calls `ForkFrom` through the control plane's single owner: it first stops the predecessor's background loop, then transfers persistence state, copies evidence while preserving pair sequence numbers and pending activity, installs the candidate kernel projection, and hands over the shared activity queue on success. The predecessor may continue serving existing connections without being fully closed beforehand. If installation fails, its queue is retained and its periodic tasks resume.

Persistence state belongs to the Registry that owns the files and transfers on reload, including the current window's expiration time. Under the Registry lock, ordinary evidence mutations queue newly numbered pairs or record each renewed pair once per window. At window closure, each pair's final deadline determines whether to list its sequence number or record an exact value. Baseline and journal encoding and I/O occur outside the Registry lock; the capacity guard instead syncs as part of the mutation batch. A dedicated lock serializes journal writers. A mutation creating a pair uses TryLock to flush pending writes; if acquisition fails, the holder or background loop writes them. A renewal frame always follows the creation frame of each pair it references. Reload holds the write lock while transferring files. The candidate Registry does not write before acceptance; rejection returns the files and current window. See [persistence and diagnostics](../configuration/dns.md#persistence-and-diagnostics) for the format, recovery semantics, and error bounds.

Runtime uses a dedicated read/write lock to order DNS evidence fan-out against reload. `ForkFrom` and the subsequent addition of the new generation to the serving set hold the write lock; fan-out holds the read lock. Every delivered response therefore either reaches the predecessor before evidence copying or also reaches the new generation. Fan-out holds the Runtime lock only to copy the generation list, and evidence copying also runs without that lock. Registry stalls therefore do not propagate to UDP ingress or TCP acceptance. Each response is parsed once, and each generation builds a bitmap under its own rules.

### Internal Resolution

`common/netutils/resolver.go` encapsulates dae's internal resolution: a stable standard-library resolver pointer, atomically replaceable server/routing policy, and an independent node-bootstrap resolver. `global.dns_resolver` overrides the internal servers; otherwise system DNS is used. `internal/daemon` switches policy when listeners are ready and reload commits. `control/daemon_dial.go` provides dae process identity and routed DNS dialing, reusing address selection from `route_dial.go` and transport lifecycle handling from `dns_upstream.go`. Proxy chains and subscription loading use their own injected bootstrap direct dialers; candidate preparation does not replace the active global dialer.

`InstallDefaultResolver` centralizes resolver validation, construction, and publication. It creates a marked socket dialer underneath, reusing outbound's `SoMarkControl`. direct uses the caller-injected resolution policy, or `net.DefaultResolver` when omitted. Each direct instance owns one `net.Dialer`; TCP, connected UDP, and unconnected UDP share its resolver and socket Control, with unconnected UDP created through `net.ListenConfig`. The independent bootstrap resolver avoids circular dependencies, atomic policy snapshots preserve reload consistency, and UDP `net.PacketConn` adaptation preserves the packet semantics required by the standard library.

## Flow Control and Routing Compilation

Routing code separates compilation, predicate evaluation, and execution:

| File | Responsibility |
| --- | --- |
| `control/routing_profile_compiler.go`, `routing_flow_compiler.go`, `routing_matcher_builder.go` | Fragment and policy expansion, predicate resource collection and sharing, and whole-program validation |
| `control/routing_state.go` | Compiled rules, dynamic client/interface updates, and userspace/kernel synchronization; does not retain the Builder after publication |
| `control/routing_instruction.go` | Instruction flags, action generation, and relative jump encoding |
| `control/routing_predicate.go` | Userspace predicate evaluation, with domain bitmaps and LPM lookup keys prepared on demand |
| `control/routing_matcher_userspace.go`, `routing_matcher_kernspace.go` | Userspace matcher construction and execution, or publication of compiled programs to the kernel |
| `control/kern/routing_abi.h` | Kernel instruction layout, predicate resources, and policy maps |
| `control/kern/routing.h` | Kernel policy selection, three-state evaluation, and control-action execution |
| `control/kern/tproxy.c` | Packet parsing, connection ownership, routing cache, and forwarding |

A policy's `rules {}` shares filter parsing, aliases, and dataset expansion with outbound rules. The ingress interface or default binding first selects a policy, then executes its three stages:

- Destination stage (`DestinationProgram`): the kernel captures candidates using the complete filter and hands them off immediately on a match, avoiding route commitment against the old address. Userspace matches the original connection and selects the first DNAT/Host target. The original five-tuple remains available for identity and replies, while the new destination becomes input to subsequent programs. Packet addresses are not modified directly in the kernel.
- Flow-control stage: accumulates `must`, `bump`, and HTTP capture flags. Actions use separate fields rather than outbound IDs, and userspace-routing requirements are handled together at the end of the control section. Ambiguous must matches caused by shared IPs do not terminate this section early; later definite must matches and capture still take effect.
- Outbound-selection stage: selects outbound and mark using the rewritten destination, address family, and original source/interface/process/policy. `must` is also computed from the new context. DNAT and Surge Host both determine the target before routing, without outbound selection undoing the mapping; a block on the new target still rejects it.

The kernel uses one shared physical instruction table, `routing_map`. Each policy's spans independently define execution order: exact API passthrough → policy DNAT and global plugin capture → policy must/bump and inspection-only MITM capture, including the control-end instruction → plugin pre-routing, policy body, ordinary plugin routing, and fallback. Shared fragments compile only once; physical storage location does not determine stage order. Go spans retain their stage, so execution skips ingress stages after selecting a target without relying on global index boundaries. Each policy's DestinationProgram references that policy's DNAT and global plugin destination rules. Exact predicates reside in a userspace suffix, and `BuildKernspace` uploads only the kernel pool. TCP connections and active UDP sessions reuse the selected destination. The kernel section retains the `MAX_MATCH_SET_LEN` limit; the userspace destination section checks capacity independently, with twice that limit.

The kernel represents unresolved routing with `control_plane_routing`. Handoff and the UDP cache share a 40-byte `routing_result` without alignment holes: `route_epoch` is at offset 0, `profile_id` at 16, `physinif` at 32, and `generation` at 36. `generation` identifies the configuration generation, while `route_epoch` independently identifies the device connection-policy version. Userspace `routingResult` embeds this result and retains the handed-off local process name or an internal request's PID/process name.

Whether a TCP packet belongs to a proxy depends only on dae owning its tuple: the handoff mailbox owns it before accept, and an accepted socket in dae's network namespace owns it afterward, with the kernel looking up the socket table directly. The proxy lifecycle starts with a SYN routed by dae and ends with dae's socket, so it needs no separate table record. There are no proxy connections on cold startup, and normal shutdown resets them all. Packets owned by neither are forwarded natively with their own marks, including connections established before the datapath and late packets arriving after dae's socket disappears.

`tcp_flow_map` is an LRU of kernel-passthrough connection properties fixed by the SYN's routing decision. Its 24-byte `tcp_flow_state` stores the device version, mark, fallback token, and SYN sequence number. Only SYNs routed by dae create or replace entries. Ordinary unmarked passthrough also has an entry, avoiding socket lookups for subsequent packets. The sender's RST is forwarded with the saved mark before deleting the entry. Token 0 is independent of fallback-generation revocation, 1 is always invalid, and other values are allocated by userspace for fallback generations per group and network type. Packets matching valid entries receive the saved mark. Device-version changes or fallback-token revocation invalidate the entry; packets then enter the transparent TCP stack, where the listening socket resets the connection so it can reconnect under current policy, or are dropped while offline. LRU eviction loses only connection properties, without interrupting the connection: forwarding becomes native with the packet's own mark, and the connection is no longer reset when fallback ends. First fragments cannot carry a mark or be split onto a proxy path, so fragments owned by a proxy, carrying a saved mark, or matching an invalid entry are dropped.

A new outbound SYN selects a new path; retransmissions with the same initial sequence number retain the existing decision. Selecting a proxy clears the tuple's old entry. A SYN-ACK answers an inbound handshake: it reuses an existing entry but never creates one. Inbound connections need no entries.

Handshake decisions and RST cleanup are serialized by a fixed-size, tuple-hashed, nonblocking atomic gate. Contention drops the current handshake packet and waits for TCP retransmission, without spinning or blocking established-connection data packets. `tcp_flow_map` and the atomic gates are shared across reloads and preserved across processes, without per-connection userspace timers or GC. Negative `TCP_LINGER2` on transparent listeners prevents prolonged FIN_WAIT2 after FIN is acknowledged, but does not imply that all closing states disappear within a fixed time.

Normal shutdown drains userspace and removes dae-owned attachments, pinned state, including obsolete map pins left by earlier versions, and internal network resources. It leaves no offline daemon and provides no standalone unload command. After complete shutdown, ordinary network routing takes over without restoring marks set by dae; connections depending on those marks may need to reconnect. A later cold startup has no entries, and connections that remained active in between continue native forwarding.

Only abnormal exits that cannot finish cleanup, such as SIGKILL, retain the kernel fallback. Valid entries keep their original marks. Proxy connections end with the process's sockets and must reconnect; packets from incomplete proxy handshakes are dropped, while other unowned packets remain natively forwarded. `unexpected_exit_behavior: bypass`, the default, lets new outbound TCP handshakes and UDP source lifecycles bypass all old routing, block, DNS/MITM capture, and destination-rewrite rules, preserving the packet's own mark and using token 0. This trades restored availability against possible traffic leakage. Setting `block` rejects new managed outbound lifecycles while retaining native forwarding and inbound replies; it does not become an inbound firewall. This setting is independent of the normal-runtime `no_connectivity_behavior`.

Starting, online, and terminal-offline states are distinct. Startup does not automatically gain abnormal-exit bypass, and a terminal Runtime cannot be published again. A new process takes over compatible pinned links left after an abnormal exit, returning online only after its listeners and new configuration generation are ready. A restart that exits before then is not a takeover: it retains those links and continues applying `unexpected_exit_behavior`. A daemon goroutine panic also skips cleanup, like SIGKILL; the instance lock prevents two daemons from running concurrently. Fallback sequence numbers are issued monotonically across abnormal exits without reusing old tokens. Normal cleanup removes the sequence table only after confirming that all old entries and attachments are gone. See [connection state and reload lifecycle](connection-lifecycle.md) for the detailed contract.

`routing_tuples_map` is a 16384-entry handoff LRU. Its 64-byte value contains the full result, expiration in monotonic seconds, the TCP initial sequence number, and the sender's local process name for userspace reevaluation of `pname()`, without field padding. TCP accept atomically retrieves and deletes the handoff. Retransmissions of the same SYN reuse it within 30 seconds without extending expiration. Non-DNS UDP reads a snapshot when establishing a source association, while DNS uses a separate per-packet handoff. Handoff capacity and expiration do not affect established TCP forwarding state.

Compiled destination predicates retain instruction ranges and target IPs. A valid address in `RouteParam.destination` indicates a selected target. A UDP source lifecycle retains its initially selected node, route, and destination rules. Rule or node updates do not change an existing lifecycle; after failure ends it, the same source port can establish a new lifecycle under current rules. `udp_destination.go` manages destination sockets and response-address restoration, while `udp_binding.go` manages source bindings.

`routingInput` is shared by destination predicates and subsequent routing, constructed consistently from original source, interface, process, MAC, DSCP, and policy. Callers pass the current destination and actual request protocol without an intermediate context or rewriting the protocol field of a kernel record. `RouteParam.Dest` retains the original destination for the current match, `destination` holds only a selected valid address, and `effectiveDestination()` supplies the target for subsequent routing and dialing. When establishing a UDP source lifecycle, the first profile and destination matcher are retained. Later destinations reuse those rules, and previously matched destinations remain fixed, including original addresses that matched no rewrite. Only after the lifecycle ends do new packets reroute under current interface policy and configuration.

`routeDestination` skips the selected policy's ingress stages, evaluates once starting at flow control, produces a pure `routeDecision`, and then selects the dialer. Outbound selection, block, and connectivity fallback do not change the selected destination; the forwarding entry point prevents dialing on block. IP rewriting preserves the logical domain and Host/SNI, does not recursively apply DNAT, and does not retrigger API ingress passthrough. Surge literal IP Host entries and native DNAT share these semantics. Domain Host entries do not automatically create DNAT or expand capture. `use-local-host-item-for-proxy` controls whether an already captured proxy connection retains the Host static DNS address.

Plugins declare capture scope and routing behavior with `HTTPScope{Scope, PreserveRoute}`. By default, routing occurs after HTTP processing; inspection-only scopes explicitly set `PreserveRoute: true`. Surge classifies scripts, URL Rewrite, and Map Local per module as request-routing features, preserving domain, port, and exclusion conditions. The kernel captures these candidates in the destination-processing prefix and uses `control_plane_routing` to indicate that userspace must select the outbound. Ordinary MITM retains valid kernel routing. Client admission is independent of the final upstream route: admitted requests run rewrites first, then decide block/direct/proxy against the final destination. Clients not admitted, or requests outside the exact scope, use ordinary connection routing.

The HTTP capture sections for post-processing routing and route preservation each have a conditional-block entry, using an internal HTTP client-admission predicate and the generic `ConditionalJump` action. The first entry into either section checks admission against device overrides and client rules, reusing the result within that routing evaluation. Rejection skips the entire section without reading its domain, IP, port, or other match conditions. Connections with no HTTP capture, or already terminated by earlier rules, do not query the HTTP client table. Kernel and userspace interpreters use the same section entries and relative jumps. Diagnostics mark denied capture rules as `client_not_allowed`; independent DNAT, must/bump, DNS, and ordinary routing are unaffected by this admission check.

Control-plane responsibilities are divided by file. `route.go` decides whether to reuse or recompute routing and commits pure policy results. `routing_input.go` centralizes input construction, `route_dial.go` selects nodes and marked dialers, and `route_log.go` logs routing. `destination_matcher.go` selects IP targets; `udp_destination.go` manages destination sockets and reply-address restoration, while `udp_binding.go` manages source-lifecycle kernel bindings. `mitm.go` handles plugin integration and connection admission. `http_target.go` shares target resolution, DNS candidates, and DestinationRule evaluation; `http_route_plan.go` builds per-request plans; `http_dial.go` performs actual upstream dialing and accounting. `mitm_download.go` manages background client lifecycle and daemon identity. HTTP Host accepts a planner whose plan determines the target, route, and transport resources.

A node's `groupBinding` stores successful latency statistics, recovery-window configuration, and completion state under the shared path's lock. The shared path owns failure facts and recovery observation times. Recovery verification reuses individual tests and the existing connectivity scheduler; failures do not enter the latency window. The automatic-selection controller handles live-node takeover, post-switch verification requests, layered election, upgrade checks, and probe demand, deciding synchronously on node notifications. Physical sessions without traffic or probe demand can sleep and be recreated on demand while retaining stable logical candidate identity. Uncompressed rank/select arrays used during userspace Trie construction are local temporary data; the object retains only compact indexes needed for queries.

Final HTTP requests and script subrequests use the same plan-building logic, selecting targets and routing before connection-pool lookup. HTTP/3 forwarding matches UDP rules, while script subrequests independently match TCP rules. Both match DestinationRule after rewriting and preserve the original source and interface policy. The original authority uses the intercepted IP, with proxy connections sending the domain according to `dial_target_override`. Other authorities have no client-selected address and use system resolution to form candidate IPs before DestinationRule, flow, and routing evaluation. Request-routing scopes determine their initial route after HTTP processing even if they change only the path; only inspection-only scopes reuse existing decisions. Each original connection has its own pools, keyed by URL/TLS authority, candidate dial address, outbound, node, mark, and fallback state, with at most 32 reusable pools cached. `planned_transport.go` retains in-flight responses from evicted pools and closes those pools only after the responses finish, avoiding disruption of concurrent HTTP/3 streams. Closing the connection releases all pools. HTTP requests collect complete candidate plans before pool lookup; background downloads consume addresses on demand from the same candidate iterator and stop after connecting successfully. Each candidate address is routed independently. Blocked addresses are not dialed, and a request is rejected if all addresses are blocked. When the proxy receives a domain, candidate addresses routed to the same node share one dial. Failed TCP candidate connections retry before any HTTP data is sent. HTTP/3 does not implicitly fall back to TCP after handshake failure. Byte accounting belongs to the actual upstream connection. Unknown hostnames reuse DNS mappings for the effective IP and are rejected if ambiguity cannot be resolved; explicit IP URLs do not borrow mappings for other logical domains.

The shared rule pool uses 24-byte `match_set` entries, with each interface policy expressing execution order through `uint16` instruction indexes. The compiler generates actions directly, and action type determines field meaning. A nonterminal instruction's `mark` stores a forward jump distance. A definite OR match jumps to the clause end to apply that clause's negation and subsequent action; a definite AND failure jumps directly to the next rule, skipping the failed rule's remaining predicates and actions. `ConditionalJump` skips the entire rule block when its condition fails; failure of a preceding AND clause also jumps directly to the block end. Jump distances use policy execution order as their coordinate system, allowing the userspace cursor to advance across physical fragments. Shared or repeated fragments need no internal jump rewriting and do not enlarge the policy table. Interface-listener updates change only match values, preserving jump metadata.

`condition -> use()` compiles into an entry predicate and a shared body. Each level's conditions retain independent boundaries rather than being copied into every rule. The compiler verifies that blocks are either nested or disjoint, entry and body belong to the same stage, and jump targets land on complete rule boundaries. DNAT capture and flow control wrap conditional blocks separately. Userspace exact destination predicates retain full conditions and select the first rewrite rule against the original destination.

The interpreter separates predicate evaluation from action execution. Clauses use three states: no match, ambiguous, and definite match. OR takes the stronger result, and negation leaves ambiguity unchanged. Completed AND clauses need only accumulate an ambiguity flag; failure immediately ends the rule, with no separate failed state. An ambiguous entry records only its block-end position, and terminal actions inherit ambiguity within that boundary. Nested blocks keep the farthest active ambiguity boundary; passing it automatically clears ambiguity without a runtime scope stack. Entry ambiguity alone does not trigger capture, and conditions inside the block can still exclude candidates. `must` uses the same three states, with a definite must overriding earlier ambiguous must results and the final decision made at the end of the control section. The program counter, ambiguity boundary, and action result form a pointer-free `route_state`. `route_apply` is independently verified as a global BPF subprogram, isolating predicate branches from combinations of action and loop states. Domain snapshots and admission caches needed by predicates remain in the evaluation context. The routing entry point receives pointer-free packet fields and is independently verified as a global BPF subprogram, preventing packet-parsing and connection-branch states from multiplying routing-iteration paths. Input and pointer-free action state reuse the entry point's per-CPU scratch area, and the selected policy ID is written back to that input. Policy and domain-snapshot pointers stay inside the evaluator. The compiler guarantees complete rule structure and valid outbound arguments; the kernel still checks policy, instruction, domain-index, and jump bounds.

The kernel's `route_step_result` indicates only whether interpretation should continue or stop; the actual routing decision lives in `route_state.result`. `route_step()` inlines instruction fetch, predicate evaluation, AND/OR, negation, and conditional jumps. Only a matched terminal action calls `route_apply()`; nonmatching rules and condition short-circuits do not enter the action subprogram. `route()` and `route_apply()` retain independent verification boundaries, while connectivity lookup and result encoding use inline functions. LPM and HTTP client-admission lookups use separate stack frames, decoupling temporary lookup-key storage from rule traversal. The loop bounds only the maximum number of steps; forward jumps determine the actual instruction-fetch position.

Userspace runs the same three-state logic and single-jump-distance instructions for both ordinary routing and destination predicates. The cursor tracks physical instruction position and logical execution position, sharing the same advance operation for ordinary short-circuiting and conditional-block jumps. Zero-distance jumps and jumps beyond the whole program return errors. Userspace queries domain bitmaps or constructs the relevant LPM key only when the corresponding predicate actually executes, reusing the result within one evaluation. Pure port matches and short-circuited paths do not prepare these resources.

Domain bitmaps are indexed by independent domain-condition IDs. Duplicate domain conditions, including the same positive set used by negated conditions, share an ID. Static LPM sets can also be reused across programs. On the first domain condition for a packet, the kernel takes a domain-mapping snapshot and reuses the same pair of bitmaps for remaining conditions. A missing mapping is also remembered, with a fresh lookup for the next packet. Dynamic `client()` sets use separate slots so membership updates do not modify static match conditions. Interface changes synchronize both sides; userspace destination instructions are never written to kernel tables.

The UDP routing cache identifies a lifecycle by source IP and source port, using a 24-byte key without destination or policy. It stores and restores the complete `routing_result` directly, without field conversion, preserving the initial ingress outbound, mark, must, capture flags, interface, profile, MAC, DSCP, protocol, device routing version, and reload rule version. With expiration, timer, lock, and fallback token, the cache value is 72 bytes without alignment holes. At lifecycle end, the token field is overwritten with 1 as a closed marker because the token is no longer needed. Process predicates read ownership storage on the sending socket itself. UDP idle timeout, device routing-version invalidation, reload rule-version invalidation, fallback-token revocation, and userspace source binding jointly constrain the lifecycle; subsequent packets reroute under current rules once it ends.

UDP flow-direction state records the first packet's direction by five-tuple. Packets entering through LAN ingress or sent locally begin outbound flows and are routed by rules. Packets on LAN egress with no state, such as port-forwarded traffic, begin inbound flows whose replies go direct. WAN ingress precedes NAT and the firewall, so only packets destined for local sockets other than dae's own begin inbound flows there, such as a local WireGuard service. Forwarded flows establish state at LAN egress after NAT. Inbound flows establish state only after receiving a reply; until then, a 16384-entry pending-reply LRU stores the second of the latest packet. The first packet in the opposite direction within the idle timeout, at WAN egress for a local service or LAN ingress for a LAN host, establishes inbound state. Unanswered packets, such as spoofed-source traffic to a WireGuard port, only churn this LRU without occupying the state table or causing new flows to be dropped because that table is full. Under flooding, an inbound flow evicted before its reply has that reply routed as outbound. Inbound flows reaching local services through port redirection or DNAT have no matching socket at WAN ingress. Their replies still lack state when they reach WAN egress after reverse NAT; conntrack identifies them as replies, starts inbound flows, and sends them direct. Replies relayed by dae through dae0 belong to userspace associations and begin outbound flows when no state exists. Local-process replies to full-cone relay sources therefore still follow routing rules and are not misclassified as inbound by conntrack direction. State is deleted after both directions have been idle for 300 seconds. Packets record only their second; when the timer fires, it checks idle duration and rearms for the remaining time if needed. The timer retains the program that installed its callback and is taken over by the current configuration generation handling packets for that flow, so long-lived flows do not keep retired generations resident.

Userspace UDP endpoints and Anyfrom reply sockets each keep an idle deadline. Activity extends it under the owning lock. Once the timer is first installed, its callback checks the latest deadline, rearming for the remaining duration if it fires early and removing the corresponding instance and closing the socket only when truly expired. Ongoing activity needs no per-packet timer reset; instance-identity checks prevent old callbacks from deleting replacement connections.

UDP packet deadlines start at enqueue time. Writes on established associations set only the socket write deadline and clear it afterward, without creating a context or timer per packet. Transports without write-deadline support use a timer that closes the socket on expiration. Nonblocking transports, `netproxy.NonBlockingWriter`, use `TryWriteTo` without a deadline, write slot, or timer. A full queue or socket send buffer drops the datagram and counts it as a UDP capacity drop, not a path error, relay failure, or uploaded bytes; MITM and DNS upstream callers see only a lost datagram. smux UDP streams enqueue into the session queue. Upload bytes are counted at enqueue time, so bytes still queued when a session fails have already been counted as uploaded. Outbounds with a dedicated kernel UDP socket per association, including direct, Shadowsocks, Shadowsocks 2022, stream-cipher Shadowsocks, SSR, SOCKS5, and juicity underlay, send with `MSG_DONTWAIT` through `RawConn.Control`. `EAGAIN` drops the datagram and counts it as `socket_full`. Each such socket is a separate flow in the egress qdisc, such as cake; queueing and fairness belong to the qdisc rather than a waiting worker. Encryption layers implement `TryWriteTo` themselves, encrypting before passing data to the underlying nonblocking writer. They do not implement `Unwrap`, so finding `NonBlockingWriter` cannot bypass encryption and reach the socket directly. If the underlying transport supports only blocking writes, as with a proxy chain over a stream transport not yet adapted, `TryWriteTo` returns `errors.ErrUnsupported` without sending, and writing falls back to the blocking path with its deadline. These outbounds' `WriteTo` also never waits for send-buffer space and treats a dropped datagram as a successful write; only domain-target resolution waits. MITM HTTP/3 bridges likewise drop when the peer's queue is full. Other transports, including yamux, retain blocking writes and their deadlines. Only socket creation for new destinations, setup, MITM, and other non-socket work derive contexts with the packet deadline. Task-pool worker write slots handle generation aborts. A worker publishes the socket being written before rechecking cancellation; the aborting side first cancels the task pool, then scans slots, sets active writes' deadlines to immediate expiration, and closes their sockets in the background. Runtime therefore does not wait for blocked writes when subsequently acquiring source locks. Anyfrom replies use `MSG_DONTWAIT`, sharing `netproxy.UDPSocket` with outbounds, and never wait for send-buffer space. A full buffer drops the reply and counts it as `reply_socket_full`; a send failure, such as failure to create a reply socket, drops only that reply and counts it as `reply_send_failed`, without ending the association. Only DNS responses and zoned client addresses that raw sending cannot address serialize writes when the send buffer is full, waiting with the query deadline as the write deadline. Transports that push replies, `netproxy.PacketPusher` such as smux UDP streams, deliver them from the session receive loop instead of starting a read goroutine per socket. The handler is registered before the socket's first write, so replies always have a receiver. Because the receive loop serves all session streams, it must not block. It sends a reply directly only when the target has already been observed, an Anyfrom socket for the reply address already exists, either cached for the first reply address or found in the pool without waiting for a lock, and a single `MSG_DONTWAIT` send succeeds. All other replies, including those requiring a synchronous registry refresh for a newly observed target, a busy socket pool or new socket, raw fallback, or a full send buffer, are handed to an on-demand goroutine along with subsequent replies for that socket for ordered delivery. Like the reply-reading goroutine, this goroutine waits only for work such as observing a target or creating a socket. The queue holds at most 128 replies; excess replies or those exceeding the UDP packet-memory budget are dropped and counted as UDP capacity drops. End-of-delivery notification may come from the receive loop or a closing caller holding the source lock; the same goroutine ends the socket after its queued replies.

`Runtime` owns listener loops, kernel attachments, TCP sets, UDP endpoints, and cross-generation connection maps. Original TCP/UDP listening FDs are registered with the kernel through `SyscallConn.Control` and serve directly, without extra FD copies. `BPFState` and the control plane own only one configuration generation. Candidates prepare independent rules, domain bitmaps, LPM, interface policies, outbound state, and API observation tables, and can close independently on failure. Static rules upload only once. Before publication, old API writes are drained and only selectors and changed client LPM slots are refreshed, without rebuilding static tables or resubscribing interfaces. Profile IDs are allocated from 1 within each generation; zero denotes the userspace default policy. Copied domain evidence is projected under new conditions, and subsequent DNS observations are distributed to all still-live generations. TCX uses `link.Update` for in-place replacement, with each interface referencing a complete configuration and no global pause; switching multiple interfaces is not a single atomic transaction.

`ControlPlane` combines traffic ingress, HTTP plugins, DNS, outbounds, API settings, routing, and interface state. Operations involving only one state component belong to that component; cross-component startup, publication, and shutdown remain coordinated by the control plane. Construction validates configuration first, takes over prepared kernel resources, then builds userspace resources, outbounds, and routing before starting connectivity checks and preparing plugins. Failed candidates first cancel preparation, then follow the same shutdown order, preserving both construction and cleanup errors. Kernel-resource and userspace-request shutdown phases remain separate.

Runtime's `InterfaceManager` owns the single link netlink subscription and interface cache, with control planes and plugins borrowing scopes. Lifecycle callbacks for interface addition, deletion, and renaming remain ordered. Changes to attributes such as carrier or operstate on an identically named interface reach `HostNetworkMonitor` through coalescible notifications, without repeating binding callbacks. The monitor independently subscribes to address, route, and policy-rule events and rebuilds snapshots through complete dumps. Events are refresh hints, not proof of connectivity; subscription interruption and recovery also trigger refreshes. Closing a monitor or scope releases only its observers, while the shared link event source closes only at full process shutdown.

Persistent ingress loops dispatch by the handed-off generation. An ordinary routing-generation change retains a 30-second ingress grace period for the old generation, then stops setup and drains remaining MITM/DNS work. Preparation of the next routing candidate waits for retirement, limiting concurrent configuration resources to two generations.

Full routing-generation changes and in-place service replacement follow the same plugin-state handoff order. Before rebuilding instances, they wait for earlier control planes and protocol hosts to retire, pause new admission, drain the current old host and finish final instance persistence, then activate the successor. New requests wait for handoff subject to their own contexts; activation failure wakes waiters and returns an error. Host selection and work registration happen in the same short critical section. DNS requests and TCP/QUIC connections retain admission tokens until completion. Already-admitted work continues using the old host; its auxiliary HTTP, internal DNS, and post-rewrite routing do not wait at the new-admission barrier, avoiding a deadlock with draining.

MITM preparation transfers the admission token, upstream planner, and optional dialer keepalive reference as one owner. TCP/QUIC release them together on setup failure or protocol completion; the QUIC constructor also owns cleanup on capacity rejection. `RouteParam` carries only routing data, not lifecycle ownership. The already-admitted DNS address policy needed for routing is passed explicitly.

Each routing generation owns its protocol host, routing policy, outbounds, and connection draining together. Rebuilt plugin instances activate only on the new routing generation after the old host drains. Late TCP/QUIC setup and DNS requests requiring old-host policy admission fail with `net.ErrClosed`, even within the 30-second grace period, allowing clients to retry on the new generation. Reused-instance workers run continuously, retaining the old protocol host and normal grace period. When all instances are unchanged, the old protocol host drains asynchronously without blocking publication.

Forced abort first interrupts ingress and wakes historical hosts. Cancellation callbacks cover the entire retirement phase, so a host already inside `Close` can cancel its work immediately; the callbacks are unregistered afterward. After acquiring keepalive ownership of reused workers, abort interrupts the current old host's work without consuming the graceful-drain period, but still waits for final cleanup and persistence. Failure of final persistence or successor activation cannot roll back to an already closed instance; the daemon enters terminal cleanup.

Ordinary TCP relays and UDP sessions independently retain their selected resources. Connection-policy leases acquired late from old groups follow the successor groups' policies. Pause, stop, and abort all use `Runtime` to settle connections and kernel reply paths.

Except for automatically intercepted DNS port 53, any direct traffic not matching explicit capture or userspace-routing requirements stays on the eBPF fast path. Missing DNS mappings for positive domain conditions do not broaden capture. The kernel selects only candidate connections, while MITM's actual hostname check stays in userspace. DNS still respects `must` and the API passthrough prefix, without borrowing or replacing the route of an unrelated UDP source session.
