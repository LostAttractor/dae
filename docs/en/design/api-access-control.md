# API Authentication and Access Control

## Responsibilities and trust boundaries

The API provides management operations for local clients and browsers, as well as self-service features for LAN devices with verified identities. Administration privileges and device identity are independent dimensions: administrators can manage the overall configuration, while device self-service operations apply only to the device identified from the current connection.

| Component | Responsibility |
| --- | --- |
| `internal/daemon` | Composing API dependencies and authentication configuration; coordinating listener and control-plane publication and reloads |
| `internal/apiserver` | Listeners, HTTP request constraints, management authentication, browser sessions and endpoint authorization |
| `control` | Correlating connection endpoints with ingress evidence from the current data path; providing device identity and management operations |
| eBPF LAN hook | Observing API connections' ingress, link type and source MAC; maintaining connection evidence for that configuration generation |
| `web` | Displaying server-confirmed access modes and operation results; the server independently authorizes every request |
| `api` / `api/client` | Public data contracts and TCP/Unix client interfaces |

API traffic bypasses userspace in the kernel according to the listener endpoint's exact destination IP/port. An explicit IP is exempt only while it is assigned locally; a wildcard uses the set of local addresses matching the address families actually listened on by Go `tcp`. `0.0.0.0` may create a dual-stack socket. The routing predicate and device-routing exemptions read the same dedicated LPM address slot; the TCP port is fixed for the listener configuration. The shared host network monitor tracks all local addresses, including interfaces without default routes. Address changes wake the daemon's serialized loop, which prepares replacement kernel and userspace address sets and atomically swaps the kernel slot before publishing the userspace set under its routing lock. Preparation or publication failure preserves the old sets and is retried. Address-only updates neither rebuild the control plane nor refresh external resources, replace MITM services or count as configuration reloads. They do not trigger outbound connectivity probes. For a port-only listener, both kernel routing and device exemptions require a local destination, the TCP port and a logical LAN ingress interface with an active listener socket. The address need not belong to the ingress interface. Failed hotplug binds due to temporary port contention are retried without another link event. The LAN hook records only evidence needed for identity and does not expand transparent-proxy or MITM capture for authentication.

HTTP/TLS protocol detection on TCP listeners retains at most 128 pending connections at once, with at most 16 per source IP and a maximum 5-second wait for the first byte. Capacity is released when detection completes, a read fails or the listener closes; a source counter is removed when it reaches zero. These limits do not depend on API authentication, which has not yet completed.

## Permission model

An empty `api.listen` disables TCP listening. The Unix socket `/var/run/dae.sock` always provides the API with permissions `0600` and requires no API key. A bare port, such as `'9080'`, requires `global.lan_interface`, binds matching interfaces and follows additions/removals. It rejects enslaved interfaces because local TCP delivery uses their master. Such topologies retain their ingress identity configuration with an explicit API IP:port; binding the master instead is appropriate only when all its ports belong to the intended LAN scope. Startup is allowed when the pattern currently matches no interfaces, without falling back to all addresses. An explicit IP constrains the destination address; a wildcard listens according to system capabilities. TCP serves HTTP and HTTPS on the same port, with HTTPS using the daemon's persistent CA regardless of whether MITM is enabled. The native API accepts only the actual listening IP literal; domains are served through an HTTPS reverse proxy.

| Role | Authorization | Features |
| --- | --- | --- |
| User | HTTPS `user_key` / `admin_key` or its session Cookie; verified direct LAN when `allow_lan_anonymous` is enabled | Global status, metrics, selector reads, CA downloads and trust verification; self-settings, status and MITM verification for identified devices |
| Administrator | HTTPS `admin_key` or its session Cookie; Unix socket protected by filesystem permissions | All user features; node switching, probes, scripts, reloads, resource refreshes, cross-device management, rule explanation, routing-impact previews and pprof |

For users, `/api/status` retains statistics and common plugin state but omits every `plugins[].details` field. Full plugin reports and script notifications require administration. Role filtering uses the same runtime snapshot without changing its statistics sources or shared state.

`user_key` and `admin_key` must differ. Remote administration is unavailable without an `admin_key`; keyless LAN access always grants only user privileges. Neither key proves device identity: `/api/device...` still verifies the current LAN connection, and MAC-related operations require a genuine Ethernet identity. Remote administrators and Unix clients can manage other devices through explicit-MAC management endpoints.

All management and monitoring over TCP requires HTTPS, including anonymous LAN access. With `allow_lan_anonymous` enabled, verified direct LAN clients may use HTTP only for CA metadata, downloads and challenge creation. The challenge proof always requires HTTPS. The HTTP page does not send credentials or load management controls. Otherwise export the CA over Unix and install it through a trusted channel.

`web_origins` is the exact browser-origin allowlist shared by the API and monitoring. It applies to anonymous, key and Cookie requests and defaults to same-origin only. Configuration and requests use the same origin normalization for hostname casing, default ports and IPv6 text; the original configuration is not rewritten. CLI, SDK and Prometheus key requests without Origin are not subject to browser-origin checks but must authenticate independently.

Only an original key over HTTPS can log in; existing sessions, anonymous LAN access and implicit Unix administrator identity cannot issue or renew sessions. Response JSON contains only `role` and `expires_at`. `Set-Cookie` sets `__Host-dae-session` with `Secure; HttpOnly; SameSite=Strict; Path=/` and no `Domain`. The server validates the signature and seven-day absolute expiry. DELETE clears the browser Cookie, including expired sessions. There is no per-session revocation table; copies remain valid until expiry or rotation of the corresponding key.

`api.web` defaults to `true` and controls whether the daemon serves static pages; `make WEBUI=n` excludes pages from the binary entirely. For independent deployment, see [API and independent clients](../configuration/api-client.md). `/metrics` is always available as a user-level API without a separate switch. `api.pprof` defaults to `false`; when enabled, `/debug/pprof/` requires administrator privileges.

## LAN and device identity

The control plane looks up eBPF ingress records using the current TCP source/destination IPs and ports. Records must be no more than 30 seconds old, and the corresponding LAN hook must still be attached. Subsequent HTTP keep-alive data also refreshes ingress evidence; a new data-path generation uses its own record table.

Ethernet ingress additionally requires a directly connected return route and an ARP/NDP neighbor matching the observed source MAC. IPv6 zones, VLANs, bridges and bonds are checked against the actual ingress relationships. Pure IP LAN interfaces have no Ethernet device identity. They can grant user privileges when keyless LAN access is enabled, but cannot provide MAC-dependent device self-service operations.

`lan_interface` defines the trusted ingress scope. For pure IP tunnel ingress, authorization covers sources entering through that interface and routed subnets behind it. The interface declaration itself supplies neither encryption nor user authentication. Private addresses and forwarding headers cannot replace current ingress evidence.

Device self-service endpoints always resolve the current connection's LAN identity and require a valid Ethernet unicast MAC. An administrator key does not allow callers to choose their own arbitrary device identity. For configuration and endpoint permissions, see [Management page/API](../configuration/api.md).

## Browser requests and sessions

TCP Host must match the actual connection's IP and port, preventing DNS rebinding. Management requests carrying Origin must be same-origin or exactly match `web_origins`. Successful and error responses for an allowed origin carry the exact ACAO, credentials and `Vary: Origin`. Preflight checks only origin, method and request headers; it requires neither a Cookie nor LAN identity and grants no application privileges. Actual requests authenticate again. JSON mutations require `X-Dae-API: 1`. A Cookie request without Origin must carry an explicit `Sec-Fetch-Site: same-origin`. Management requests marked `cross-site` are always rejected and cannot be allowed by extending the allowlist.

Same-origin requires identical scheme, host and port. Same-site follows the browser's scheme/site rules and may span ports. Because the native API uses IP literals, same-site cross-origin direct access normally means two HTTPS ports on the same IP, not any two LAN addresses. The page supports only same-site direct access or a same-origin reverse proxy and does not attempt its own public-suffix/site classification. Credential-free challenge-proof GETs use independent challenge Origin binding, allow reading issued challenges, and are not subject to the cross-site restriction for management requests.

Session signatures bind role, Host and port, using that role's own key. Rotating one key invalidates only that role's sessions. Management requests use `credentials: include`; HTTP setup requests and proof GETs use `credentials: omit`. Cookies are not isolated by port, so all HTTPS services on the same host must be trusted; a dedicated management hostname is recommended. Tabs share Cookie scope and login state. Explicit Authorization takes precedence: an invalid key does not fall back to a Cookie, and an invalid Cookie does not fall back to anonymous privileges. A valid original key can replace an expired Cookie. `web_origins` is neither authentication nor a firewall; a custom client forging Origin does not gain a key or LAN identity.

The page's target is fixed at development/build time by `DAE_API_URL`, defaulting to relative `/api/`; an explicit target accepts only an HTTPS origin without a path prefix. Frontend constants and `dae-web.json` share a single parse. The daemon reads metadata from the embedded/external assets actually served and combines it with proof targets to generate CSP. Missing or invalid metadata fails rather than allowing arbitrary HTTPS destinations. The client provides neither runtime address switching nor credential storage.

## Reverse-proxy capability boundaries

Both browser-to-proxy and proxy-to-dae HTTPS are supported. The proxy verifies dae's CA, rewrites Host to the actual API IP:port, preserves the page Origin, and allows that exact origin through `web_origins`. Every upstream request must unconditionally overwrite `X-Dae-Proxy: 1`; the proxy must not inject a long-lived key. HTTP or Unix upstreams are rejected; implicit Unix administrator privileges cannot be lent to a browser.

The presence of `X-Dae-Proxy`, `Forwarded`, `X-Forwarded-*` or `X-Real-IP`, including empty values, only removes capabilities and never grants identity. Proxy requests cannot use anonymous LAN access, any self-device/self-diagnostics endpoint or browser CA/MITM verification, including public proof GETs. They retain key/Cookie management, explicit-MAC management and CA downloads. Ordinary TCP cannot reliably identify an unmarked proxy; correctly setting the marker is part of the supported deployment contract.

The browser may be same-origin with the proxy, but this proves neither genuine device identity nor browser trust in dae's CA; the proxy's TLS handshake proves only trust on the proxy side. When direct-access capability is denied, the frontend displays unavailable while management requests continue refreshing independently. See the [same-origin HTTPS reverse proxy example](../configuration/api-client.md#same-origin-https-reverse-proxy).

Monitoring requests complete authorization while holding the control-plane lock, then release it before running process-level metrics/pprof handlers. Long profiles neither block reloads nor retain references to a closed control plane. Unix monitoring and operational queries remain available while the control plane drains.

## Page access state

The page derives access state from `auth_mode` in the protected Selectors response, while `admin_enabled` distinguishes administration operations. Even after a successful login response, this query must complete before the page displays administrator or LAN access state and enables management controls.

`401` and `403` clear the corresponding management access state. Other request errors display an operation failure without inferring a new authorization state. Concurrent refresh results are applied by request generation, so an older rejection cannot overwrite privileges confirmed by a newer request. Device self-service state is loaded and verified independently; the page's management state does not replace device identity. Guest pages continue polling access state and recover automatically when another tab logs in or renews its login; remaining signed out does not repeatedly display error notifications.

## Certificate lifecycle and verification boundaries

`component/ca` provides loading, atomic initialization, public export and leaf-certificate issuance. The daemon holds an immutable CA identity borrowed separately by API and MITM; `mitm` neither reads paths nor creates a CA. Explicit paths in the top-level `certificate` section are load-only, with no fallback when missing. If the default managed directory does not exist, dae initializes a self-signed root CA so the Unix API can also export the certificate. Existing corrupted or incomplete directories do not automatically trigger identity replacement.

Reload first prepares candidate certificates and services, switching the daemon identity only after successful publication; failure preserves the active configuration. The same fingerprint reuses the original identity and leaf cache; a changed fingerprint switches API and MITM together. Protocol detection belongs only to the generic listener layer in `internal/apiserver`. The API service owns its leaf certificate and handshake generation, which trust tests use as evidence; no listener port is added and HTTP/TLS multiplexing is unchanged. Closing a listener, disabling HTTPS or changing TLS identity waits for issuance and persistence under the old identity to finish before allowing a replacement identity to use the storage directory. Handshakes that already obtained the old TLS configuration but have not yet issued a certificate are rejected. Draining requests alone does not retire the TLS identity.

Ordinary metadata reads may reuse an already accepted TLS connection and cannot serve as evidence of CA trust. API management leaf certificates are persisted by CA fingerprint and router IP and reused across access, restarts and reloads while valid. `POST /api/certificate/tests` issues a separate temporary leaf certificate and new key, creating a short-lived challenge bound to source IP, router IP, page Origin and issuance generation. The certificate belongs only to the challenge and is written neither to disk nor to the shared MITM cache.

TLS handshakes occur before the HTTP path is available. Using the actual TCP source IP and local IP, the listener selects the newest unexpired challenge certificate for that address pair, or the management certificate if no challenge exists. Clients sharing a source IP cannot be isolated by browser tab; management connections from other source IPs do not switch certificates. An HTTPS GET returns proof only if its connection used this challenge's certificate or a newer challenge certificate, then consumes the challenge. Connections using the management certificate or an older challenge return `409` and close; the frontend retries within a bounded limit. Management-certificate handshake generations are always zero, so later loading or renewal on expiry cannot serve as challenge proof. Concurrent challenges do not invalidate one another and may complete in any order. TLS session tickets are disabled, preventing an old handshake from serving as new proof through session resumption.

At most 8 challenges are retained per source IP and 64 globally; excess creation requests return `429`. They expire after one minute and do not depend on MAC or MITM generation. Challenge deadlines are independent of X.509 validity: temporary certificates allow five additional minutes of validity beyond the challenge window for client clock skew, capped by CA expiry. Expired challenges are cleaned up during handshakes and challenge requests, and expired certificates are no longer selected. Successful proof removes its challenge; once none remain for that address pair, new handshakes use the original management certificate again. A daemon restart discards temporary challenges and loads the management certificate. A browser exception previously accepted for the management certificate cannot authorize a temporary challenge certificate. New HTTPS connections relying on such an exception may fail while a challenge is valid, but the HTTP installation page remains accessible. API tests change neither the persistent management certificate, CA nor shared MITM issuance cache.

Transparent MITM verification separately holds short-lived challenges in `component/mitm/verify`, bound to device, Origin, virtual target and current runtime generation. Each verified MAC may retain at most 8 challenges and observations, with 256 globally. They expire after one minute; excess creation requests return `503`. Verification passes only after the browser receives a matching proof and an authenticated query confirms capture. CA changes clear both types of results; device or MITM-generation changes clear only interception results.

Automatic and manual browser verification share an in-progress task only while its CA, device, MITM generation and access context remain valid. Completed tasks are not cached, so a later manual test starts a new challenge. Login or access changes invalidate pending results without erasing completed CA trust or a confirmed direct-connection capability denial. Older tasks cannot overwrite newer results or retire a newer task.
