# 排队目标与验收

排队改进的目标是在相同配置下减少转发开销和可避免的等待。全进程只有一个队列、所有协议使用同一种算法，或无条件保证端到端时延，都不是目标。

## 约束与优化目标

硬约束包括明确的缓冲区所有权、有界资源准入、正确的取消与释放、可靠流的帧顺序，以及准确的丢包核账。拒绝数据报不应使健康的共享连接失效；已经提交到可靠流的字节不能选择性删除。清理有时间上限，不等于无条件保证送达。

性能目标按场景区分：

| 场景 | 观测指标 | 判断方式 |
| --- | --- | --- |
| 低负载 | 进程 CPU、每探针 CPU、时延分布、常驻内存 | 检查固定和逐包开销；稀疏小包不宜用 CPU/GB 评价 |
| 持续拥塞 | 有效吞吐、CPU/GB、交互时延、丢包、排队趋势 | 减少多余积压，同时避免载体缺少可发送数据 |
| 过载或故障 | 资源上限、其他就绪来源的进度、拒绝、取消和恢复 | 不要求继续维持正常吞吐或无条件的时延上限 |
| 机制诊断 | 控制批量、单载体或人为写者成本等变量 | 用于解释机制，不视为生产环境 CPU 效率 |

在满足硬约束和所需隔离能力的前提下，优先采用更少的排队状态和反馈机制，不应仅为改善基准比例增加自适应控制。

测量前应声明适合当前场景的筛查阈值。例如，可比的稳态大流负载可以用“吞吐保留基线的 97%、CPU/GB 不超过基线的 105%”标记回归，但这不是普遍的验收硬门槛。CPU 变化需结合绝对 CPU 时间、可用处理余量、吞吐和时延收益，以及实现复杂度一起评估。越过阈值意味着需要权衡，不是自动通过或拒绝；配对波动跨线时，结论仍不确定。

不存在通用的“游戏 p99 必须小于 120 ms”验收规则。必须同时看丢包、缺失探针、样本数和最大时延，不能通过丢掉慢探针制造改善。

拥塞窗口缩小或载体停顿，不足以证明全部等待都不可避免；应先归因额外延迟。反过来，正常等待 ACK 的在途字节也不自动属于 bufferbloat，压缩带宽时延积可能降低吞吐。

## 小规模配对比较

两侧在同一主机、相同 CPU 亲和性下运行，使用相同 Go 版本、tags、链接参数、依赖和测试夹具；矩阵运行期间不得替换二进制。默认矩阵只运行 `normal`（仅游戏探针）和 `saturated`（游戏加四条大流），每个二进制各两轮，采用 AB/BA 顺序：

```sh
SUDO="flock $HOME/.cache/dae-root-tests.lock sudo -n" \
  OUT=/tmp/queue-comparison scripts/tests/queueing/matrix.sh \
  /tmp/before.test,/tmp/after.test 2 normal saturated
```

默认拓扑是本机夹具：40 Mbit/s CAKE 上行、90 ms 回程 netem，以及 Shadowsocks 2022 / smux 链。CAKE 的 interval 参数不等于测得的载体 RTT，netem 参数也不能证明真实节点的 RTT。夹具跳过关联建立，因此建立阶段另由生命周期测试覆盖。详细路径和报告字段见[排队实验说明](testing-and-performance.md)。

smux 测试服务端将每个完整帧用一次写入交给载体，不等待攒齐多个帧。若把帧头和载荷拆成两次载体写入，可能增加加密记录、客户端读取和唤醒次数。载体分段方式是夹具的一部分，不代表所有真实服务端；归因小包 CPU 开销时，应显式比较不同分段方式。

默认比较场景通过测试专用的 `QEXP_SOCKET_SAMPLES=false` 关闭每 10 ms 的 socket 查询，避免某个实现仅因载体更多就承担更多观测系统调用。诊断场景默认仍采样，除非显式关闭。启用 socket 采样、写者自旋或 LAN 侧 QUIC 客户端时，不输出归一化 CPU 指标。纯游戏场景输出 `cpu_us_per_game_packet`，分母为窗口内发出的探针，必须结合交付和丢包数解读。

客户端进程也生成负载并记录探针回包，因此其 CPU 是比较用的夹具指标，不是单独的 daemon CPU。交付节奏会改变生成器和记录器的唤醒；应使用调用栈归因或提供相同隔离能力的参照，不能把混合负载 CPU 差值全部归为队列调度开销。

## 机制消融

`ablate.py` 为完整调度器、关闭 CoDel、保留 CoDel 但移除基于速率的公平份额保护生成独立 Go overlay。输出目录必须尚不存在；源码不再唯一匹配预期变换时拒绝生成。它不修改生产文件，也不增加运行时配置。消融版本保留相关状态和测试，用于识别策略作用，不用于测算完整删除后的 CPU 或内存节省。

在开发环境中运行：

```sh
work=$(mktemp -d)
python3 scripts/tests/queueing/ablate.py "$work/variants"
for variant in base no-codel no-rate-guard; do
  GOWORK=off go test -count=1 -overlay="$work/variants/$variant.json" \
    ./pkg/outbound/netproxy/fq -run '^TestDatagramQueueScenarios$' -v
done
```

确定性载体场景覆盖：低于字节上限的持续积压、与 16 条可靠流共享且按公平份额发送的数据报流、更慢的载体，以及跨批次的数据报。混合流场景使用 64 KiB 批次。报告的排队时间截止于首次出队，不是最后一个字节写完，不包含序列化耗时和网络 RTT。发送、丢弃和剩余排队数量必须解释全部输入，清理后共享预算必须归还；时延分布须结合丢包一起看。这些是机制检查，不是真实网络性能验收；针对完整策略的测试在消融版本上可能按预期失败。

## 报告有效性

报告的 `conditions` 保存实际采用的拓扑、负载、载体限制、服务端分帧方式、写者延迟、采样模式、测量窗口和运行平台。统计工具不把未完成窗口、迟到样本、缺失的必要丢包核账或未核账丢包纳入性能汇总；条件缺失或不同的运行不配对。无效数量和最差有效性检查仍显示，被排除的配对会在 stderr 说明原因。无效、条件不一致或缺失的配对会返回非零退出状态；这验证的是测量是否有效，不是性能是否达标。

矩阵在 `OUT/artifacts` 中记录构建参数和每个二进制的一次指纹，并在实验开始前拒绝 Go 版本或构建参数不同的组合；源码版本可以不同。指纹只证明产物身份，不证明正确性或完整可比性，仍需核对源码和夹具差异。按重复轮次配对，不混比历史运行。两对结果用于筛查，不构成置信区间或自动批准。

先由配对比较定位问题，再显式选择诊断场景。不反复跑完整诊断矩阵，也不为越过门槛而更换拥塞控制、修改 socket 配置或丢包策略。
