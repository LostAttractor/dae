# API 鉴权与访问控制

## 职责与信任边界

API 向本地客户端和浏览器提供管理操作，同时向经过身份验证的 LAN 设备提供本机自助功能。管理权限与设备身份是两个独立维度：管理员可以管理整体配置，设备自助操作只能作用于当前连接识别出的设备。

| 组件 | 职责 |
| --- | --- |
| `internal/daemon` | 组装 API 依赖与鉴权配置，协调监听器和控制面的发布及重载 |
| `internal/apiserver` | 监听入口、HTTP 请求约束、管理鉴权、浏览器会话和端点权限检查 |
| `control` | 将连接端点与当前数据路径的入口证据关联，提供设备身份及管理操作 |
| eBPF LAN hook | 观察 API 连接的入口、链路类型和源 MAC，维护该配置代的连接证据 |
| `web` | 展示服务端确认的访问模式和操作结果；服务端独立执行每个请求的授权 |
| `api` / `api/client` | 公开数据契约及 TCP/Unix 调用接口 |

API 流量按监听端点的精确目的 IP/端口在内核直通：显式 IP 仅在本机持有该地址时旁路，wildcard 使用与 Go `tcp` 实际监听地址族一致的本机地址集合；`0.0.0.0` 可能创建双栈 socket。路由谓词与设备路由豁免读取同一个独立 LPM 地址槽，TCP 端口由监听配置固定。共享的主机网络监视器跟踪所有本机地址，包括没有默认路由的接口；地址变化唤醒 daemon 的串行循环，预先构建替代的内核及用户态地址集合，在路由锁内先原子替换内核槽，再发布用户态集合。准备或发布失败时保留原集合并重试。仅地址变化不会重建控制面、刷新外部资源、替换 MITM 服务或计为配置重载，也不会触发出站连通性探测。裸端口模式下，内核路由旁路与设备路由豁免均要求目的为本机地址、TCP 端口匹配，且逻辑 LAN 入口上已有实际监听 socket；目的地址不必属于该入口接口。热插拔时若端口临时被占用，监听器会自行退避重试，无需再次触发接口事件。LAN hook 只记录身份所需证据，不为鉴权扩大透明代理或 MITM 的捕获范围。

TCP 监听的 HTTP/TLS 协议识别最多同时保留 128 条待识别连接，每个来源 IP 至多 16 条，等待首字节最多 5 秒。额度在识别完成、读失败或监听关闭时释放，来源计数归零即删除；这些限制不依赖尚未完成的 API 鉴权。

## 权限模型

`api.listen` 留空时不监听 TCP；Unix socket `/var/run/dae.sock` 始终提供 API，权限为 `0600`，不要求 API key。仅填写端口（如 `'9080'`）必须配置 `global.lan_interface`，绑定匹配接口并跟随增删；由于本机 TCP 流量交付给 master，该模式拒绝从接口。此类拓扑可以保留入口身份配置并使用显式 API IP:port；仅当 master 的全部端口都属于预期 LAN 范围时才应改绑 master。pattern 暂无匹配时允许启动，不回退为全部地址。显式 IP 限定目的地址，wildcard 按系统能力监听。TCP 同一端口提供 HTTP 和 HTTPS，HTTPS 使用 daemon 的持久化 CA，与 MITM 是否启用无关。原生 API 仅接受实际监听 IP 字面地址，域名通过 HTTPS 反代提供。

| 权限 | 授权方式 | 功能 |
| --- | --- | --- |
| 普通用户 | HTTPS `user_key` / `admin_key` 或其会话 Cookie；开启 `allow_lan_anonymous` 后的已验证直连 LAN | 全局 status、metrics、selector 读取、CA 下载与信任验证；已识别设备的自身设置、状态与 MITM 验证 |
| 管理员 | HTTPS `admin_key` 或其会话 Cookie；受文件权限保护的 Unix socket | 包含普通权限；节点切换、探测、脚本、重载、资源刷新、跨设备管理、规则解释、路由影响预览、pprof |

普通用户的 `/api/status` 保留统计和插件通用状态，省略所有 `plugins[].details`；完整插件报告及脚本通知仅管理员可读。角色过滤使用同一份运行时快照，不改变统计数据源或共享状态。

`user_key` 与 `admin_key` 必须不同。没有配置 `admin_key` 时远程管理不可用；LAN 免 key 永远只授予普通权限。两类 key 都不证明设备身份：`/api/device...` 仍校验当前 LAN 连接，涉及 MAC 的操作要求真实以太网身份。远程管理员和 Unix 客户端可以通过显式 MAC 管理接口操作其他设备。

通过 TCP 访问管理接口、metrics 和 pprof 均需 HTTPS，已验证的匿名 LAN 也不例外。开启 `allow_lan_anonymous` 后，已验证的直连 LAN 客户端可通过 HTTP 读取 CA 信息、下载证书和创建信任挑战；挑战证明始终要求 HTTPS。HTTP 安装页不发送凭据，也不加载管理功能。未开启匿名 LAN 时，请从 Unix socket 导出 CA，再通过可信渠道安装。

`web_origins` 是 API 与 monitoring 共用的浏览器精确来源白名单，适用于匿名、key 和 Cookie 请求，默认仅同源；配置与请求共用 origin 规范化，统一主机大小写、默认端口与 IPv6 文本。原始配置不被改写。无 Origin 的 CLI、SDK、Prometheus key 请求不受浏览器来源检查约束，但必须独立鉴权。

只有 HTTPS 原始 key 可以登录；已有会话、LAN 匿名与 Unix 隐式管理员身份均不能签发或续期。响应 JSON 仅含 `role` 和 `expires_at`，`Set-Cookie` 写入 `__Host-dae-session`，使用 `Secure; HttpOnly; SameSite=Strict; Path=/`，无 `Domain`。服务端校验签名与七天绝对到期时间。DELETE 清除浏览器 Cookie，包括过期会话；无逐会话吊销表，复制件直到到期或相应 key 轮换才失效。

`api.web` 默认 `true`，控制 daemon 提供静态页面；`make WEBUI=n` 完全不编入页面。独立部署见 [API 与独立客户端](../configuration/api-client.md)。`/metrics` 始终作为普通 API 提供，无独立开关；`api.pprof` 默认 `false`，启用后 `/debug/pprof/` 使用管理员权限。

## LAN 与设备身份

控制面使用当前 TCP 源、目的 IP 和端口查找 eBPF 入口记录。记录必须在 30 秒内，且对应 LAN hook 仍然挂载。HTTP keep-alive 的后续数据同样刷新入口证据；新数据路径代使用自己的记录表。

以太网入口还要求回程直连路由和 ARP/NDP 邻居与所观察的源 MAC 一致；IPv6 zone、VLAN、网桥和 bond 按实际入口关系校验。纯 IP LAN 接口没有以太网设备身份，开启 LAN 免 key 后可以提供普通权限，但不能提供依赖 MAC 的设备自助操作。

`lan_interface` 定义受信任的入口范围。纯 IP 隧道入口的授权范围包含从该接口进入的来源及其后方路由子网；接口声明本身不提供加密或用户认证。私网地址和转发头 均不能代替当前入口证据。

设备自助端点始终解析当前连接的 LAN 身份，并要求有效的以太网单播 MAC。管理 key 不允许调用者任意指定自己的设备身份。配置说明及端点权限见[页面/API](../configuration/api.md)。

## 浏览器请求与会话

TCP Host 必须是实际连接的 IP 与端口，阻止 DNS rebinding。带 Origin 的管理请求需同源或精确匹配 `web_origins`；允许来源的成功与错误响应携带精确 ACAO、credentials 与 `Vary: Origin`。预检只检查来源、方法和请求头，不要求 Cookie 或 LAN 身份，不授予业务权限；实际请求重新鉴权。JSON 修改请求要求 `X-Dae-API: 1`。Cookie 请求没有 Origin 时，必须有明确 `Sec-Fetch-Site: same-origin`；管理请求标记为 `cross-site` 时始终拒绝，不能靠扩展白名单放行。

同源要求协议、主机和端口都相同；同站按浏览器的协议/站点规则判断，可以跨端口。原生 API 使用 IP 字面地址，因此同站跨源直连通常是同一 IP 的两个 HTTPS 端口，不等于任意两个 LAN 地址。页面仅支持同站直连或同源反代，不尝试自行实现公共后缀/站点判断。无凭据的挑战证明 GET 使用独立的挑战 Origin 绑定，允许读取已签发挑战，不套用管理请求的跨站限制。

会话签名绑定 role、Host 和端口，使用该权限自己的 key；轮换某一 key 只使该角色的会话失效。管理页请求使用 `credentials: include`；HTTP 安装页请求和证明 GET 使用 `credentials: omit`。Cookie 不按端口隔离；同主机所有 HTTPS 服务必须可信，建议专用管理主机名。标签页共享 Cookie 作用域与登录状态。显式 Authorization 优先，错误 key 不回退 Cookie，错误 Cookie 不回退匿名权限；正确原始 key 可以替换过期 Cookie。`web_origins` 不是认证或防火墙，自定义客户端伪造 Origin 不能获得 key 或 LAN 身份。

页面目标由开发/构建时的 `DAE_API_URL` 固定，默认相对 `/api/`，显式目标仅接受 HTTPS origin，无路径前缀。前端常量和 `dae-web.json` 共用一次解析；daemon 从实际服务的内嵌/外部产物读取元数据并与证明目标生成 CSP，缺失或非法时失败，不扩大为任意 HTTPS。客户端不提供运行时地址切换或凭据存储。

## 反向代理的能力边界

支持浏览器到代理、代理到 dae 两段 HTTPS。代理验证 dae CA，将 Host 重写为实际 API IP:port，保留页面 Origin，并在 `web_origins` 中允许该精确来源；每个上游请求无条件覆盖 `X-Dae-Proxy: 1`，不注入长期 key。HTTP 或 Unix 上游被拒绝；Unix 隐式管理权限不能借给浏览器。

`X-Dae-Proxy`、`Forwarded`、`X-Forwarded-*` 和 `X-Real-IP` 的存在（包括空值）仅移除能力，不参与身份授予。代理请求禁止匿名 LAN、全部自身设备/自身诊断接口和浏览器 CA/MITM 验证（包括公开证明 GET），保留 key/Cookie 管理、显式 MAC 管理及 CA 下载。普通 TCP 无法可靠识别未标记的代理，正确设置标记是支持的部署契约。

浏览器可能与代理同源，但不能据此推导真实设备身份或浏览器信任 dae CA；代理的 TLS 握手只证明代理侧信任。前端对直连能力拒绝显示 unavailable，管理请求仍独立刷新。示例见[同源 HTTPS 反向代理](../configuration/api-client.md#同源-https-反向代理)。

监控请求在持有控制面锁时完成授权，再释放锁执行进程级 metrics/pprof handler。长时间 profile 不阻塞重载，也不保留关闭后的控制面引用；Unix 监控与操作查询在控制面排空期间仍可用。

## 页面访问状态

页面以受保护 Selectors 响应中的 `auth_mode` 作为访问状态来源，`admin_enabled` 区分管理操作。登录响应成功后仍需完成该查询，才能显示管理员或 LAN 访问状态并启用管理控件。

`401` 和 `403` 清除相应的管理访问状态。其他请求错误显示操作失败，不推导新的授权状态。并发刷新按请求代次应用结果，较早请求的拒绝不能覆盖较新请求已经确认的权限。设备自助状态独立加载和校验，页面的管理状态不替代设备身份。Guest 页面继续定期查询访问状态，可在另一标签页登录或重新登录后自动恢复；持续未登录不会反复弹出错误通知。

## 证书生命周期与验证边界

`component/ca` 提供加载、原子初始化、公开导出和叶证书签发能力。daemon 持有不可变 CA 身份，API 与 MITM 分别借用；`mitm` 不读取路径、不创建 CA。顶层 `certificate` 显式指定的路径只加载，不存在时不回退。默认托管目录不存在时初始化自签名根 CA，使 Unix API 也能导出证书，已有损坏或不完整目录不自动更换身份。

重载先准备候选证书与服务，发布成功后才切换 daemon 身份；失败保留活动配置。相同指纹复用原身份与叶证书缓存，更换指纹时 API 和 MITM 同步切换。协议识别仅属于 `internal/apiserver` 的通用监听层。API 服务持有自己的叶证书和握手代次，信任测试使用该证据；不增加监听端口或改变 HTTP/TLS 分流。关闭监听器、禁用 HTTPS 或更换 TLS 身份时，先等待旧身份的签发与落盘完成，再允许替代身份使用存储目录；已取得旧 TLS 配置但尚未签发的握手被拒绝。仅排空请求不退役 TLS 身份。

普通元数据读取可能复用已放行的 TLS 连接，不能作为 CA 信任证据。API 的管理叶证书按 CA 指纹和路由器 IP 持久化，有效期内访问、重启和重载均复用。`POST /api/certificate/tests` 另行签发临时叶证书和新密钥，创建绑定源 IP、路由器 IP、页面 Origin 与签发代次的短期挑战，证书只由挑战持有，不写入磁盘或共享 MITM 缓存。

TLS 握手发生在 HTTP 路径可用之前。监听器根据真实 TCP 源 IP 和本地 IP，在未过期挑战中选择该地址对最新的证书；无挑战时使用管理证书。共享源 IP 的客户端无法按标签页隔离，其他源 IP 的管理连接不切换证书。HTTPS GET 只有在连接使用本次或更新挑战的证书时才返回证明，随后消费该挑战；管理证书与更早挑战的连接返回 `409` 并关闭，前端有界重试。管理证书的握手代次始终为零，后续加载或到期更新也不能充当挑战证明。并发挑战互不作废，完成顺序不受限。TLS session ticket 禁用，旧握手不能通过会话恢复充当新证明。

挑战每个源 IP 最多保留 8 个、全局最多 64 个，超额创建返回 `429`；一分钟过期，不依赖 MAC 或 MITM 代次。挑战期限与 X.509 有效期独立，临时证书向后额外预留五分钟客户端时钟偏差，不超过 CA 到期时间。过期清理在握手和挑战请求中执行，过期证书不再参与选择。证明成功移除对应挑战；该地址对没有剩余挑战后，新握手恢复原管理证书。daemon 重启丢弃临时挑战并加载管理证书。先前对管理证书接受的浏览器例外不能放行临时挑战证书；挑战有效期内依赖例外的新 HTTPS 连接可能失败，HTTP 安装页仍可访问。API 测试不会改变持久化管理证书、CA 或共享 MITM 签发缓存。

透明 MITM 验证由 `component/mitm/verify` 单独持有短期挑战，绑定设备、Origin、虚拟目标与当前运行代次；每个已验证 MAC 最多保留 8 条挑战及观测，全局最多 256 条，一分钟后过期，超额创建返回 `503`。浏览器收到匹配 proof 且经鉴权查询确认捕获后才通过。CA 变化清除两类结果，设备或 MITM 代次变化只清除拦截结果。

浏览器的自动与手动验证仅在 CA、设备、MITM 代次和访问上下文仍有效时共享进行中的任务。已完成任务不缓存，之后手动测试会创建新挑战。登录或访问状态变化使未完成结果失效，但不清除已完成的 CA 信任或已确认的直连能力拒绝。旧任务不能覆盖新结果，也不能清除更新的进行中任务。
