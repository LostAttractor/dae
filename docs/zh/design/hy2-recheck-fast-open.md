# 统一健康检查与 HY2 FastOpen 失败处理

同一代理路径使用一份健康状态、成功延迟、健康凭据和恢复观察。`tcp4`、`tcp6`、`udp4`、`udp6` 只分别记录已发现的网络能力。HY2 的连接错误通过这个连通性检查循环确认。

## 设计取舍：统一代表探针

设计前提是：节点通常不会只发生单一网络栈的故障。dae 的故障转移用于探测 dae 与代理节点之间连接的故障。经代理访问配置 DNS 检测端点的探针提供代表性连通性证据，不承担逐一诊断代理出口各协议、地址族和业务目标可达性的职责。

为每个节点持续独立维护各网络模式是否可用，需要反复尝试大量额外连接。因此 dae 明确不采用按网络模式分别维护健康状态、恢复窗口或切换验证的设计。这是为控制探测开销作出的明确取舍：代表模式故障会使整个路径不可用；只影响其他模式的异常可能无法由健康检查识别。

能力发现与健康检查分开。初次发现以及未知能力的后续发现可以分别尝试各模式；已确认的能力持续保留，普通超时不会撤销能力。按 `tcp6 → tcp4 → udp6 → udp4` 顺序选择第一个已支持模式作为代表，后续日常检查、业务故障确认、恢复观察和切换前验证均使用该代表探针。代表探针失败时，不通过轮换其他已支持模式来维持路径健康。

同一路径所有已支持模式共用代表探针的成功凭据。不同目标网络的并发验证合并，恢复窗口末次成功也直接用于切换；网络能力仍决定路径能否承接对应请求。新故障或 Session 世代变化使共享凭据失效。未知能力必须先实际发现，不能由共享健康状态推导出来。各组共享实际探测，保留各自的延迟统计参数和 `failure_recovery` 时长。

## 业务错误与确认检查

路径处于 healthy 时，首个合格的上游错误请求检查并进入 confirming。所有模式的后续错误合并到当前确认，不重启检查，也不增加失败代次。已不可用路径的业务错误不重置恢复退避。

确认期间，已选中的路径可以继续服务；新选择需要有效健康凭据。代表探针成功恢复路径，失败撤销所有已支持模式的可用性。旧检查结果不能清除后来发生的失败。已确认支持的模式保留其协议能力，普通超时不会将其标记为永久不支持。

| 错误 | 行为 |
| --- | --- |
| 上游读写错误、上游操作超时、FastOpen 应答超时或协议错误 | 请求共享路径的确认检查 |
| 调用方取消或 deadline、本地清理、目标拒绝、已知容量限制 | 处理当前操作，不请求确认 |
| 正常 EOF | 正常半关闭 |
| owner 已确认 QUIC 连接失效 | 进入 Session 故障与恢复流程 |
| 检查确认代理认证失败 | 阻断路径重试，等待环境变化或显式重查 |

同一路径使用一个检查调度器，网络操作共用进程级并发预算。常规健康检查只使用代表模式，失败时最多重试一次；恢复和切换前的一次性验证共用代表探针，受各自总预算限制。未知能力的发现需要实际探测所请求模式，并取得或复用本轮代表探针凭据。常规检查两次尝试的错误均保留，第二次出现的认证失败不能被第一次超时掩盖。

## FastOpen 应答期限

首次 `Read` 开始解析代理应答时，设置最多 8 秒的内部 read deadline。有效 deadline 始终取内部期限与调用方期限中较早者；调用方延长或清除期限不能延长内部预算。应答成功后恢复最新的调用方 read deadline。

更短的调用方 deadline 中断解析时，关闭当前连接，不恢复读到一半的协议头。该错误保留调用方来源，不触发路径确认。内部预算耗尽属于协议侧错误，会请求确认。

8 秒从实际读取应答开始计算。正常 TCP relay 在连接返回后启动上游读取；从不调用 `Read` 的独立消费者依赖 `Close` 或 QUIC 存活机制结束连接。请求头发送受 DialContext/Handshake 的预算约束。

## 逻辑连接与共享会话生命周期

FastOpen 终结失败保存原始错误，Abort 当前 stream 的 Lease，并取消该 stream 的 I/O。relay 收到 Abort 后关闭连接并向 TCP 客户端发送 RST。后续读写返回保存的错误，`Close` 幂等释放资源。目标拒绝同样终止当前连接，但不触发路径确认；成功后的正常 EOF 继续半关闭。

不可恢复的 HY2 单流错误先执行带来源和资源信息的 stream Abort，再进入通用错误包装。单流失败不关闭共享 QUIC 或兄弟 stream，也不重放业务数据。共享 QUIC 失效由资源 owner 执行 Abort、cleanup 和 Connect。

健康检查不会主动销毁仍显示 connected 的共享 Session。无排队时，FastOpen 内部应答等待最多 8 秒，随后两次确认探测各受现有 8 秒预算约束；排队与共享会话恢复另受各自生命周期控制，不能据此承诺固定的整体恢复时限。
